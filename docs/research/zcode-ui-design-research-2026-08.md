# ZCode UI 设计调研报告

> 调研对象：本机运行中的 `/Applications/ZCode.app` 桌面应用
>
> 调研时间：2026-08-25（Asia/Shanghai）
>
> 调研范围：工作区主界面、左侧项目导航、MainView、Composer、右侧工作面板、全局命令中心、设置工作区及其主要设置页。
>
> 证据等级：本文以当前运行窗口的可访问结构和截图为直接证据；尺寸为当前窗口截图中的近似值，交互意图属于基于行为的设计推断。

## 1. 结论摘要

ZCode 的核心 UI 不是单一聊天页，而是一个「三 dock 工作台」：

```text
┌─ 左侧工作区导航 ─┬─ MainView / 会话主区 ─────────────┬─ 可选右侧工作面板 ─┐
│ 项目、任务、设置  │ 新任务、消息流、Composer           │ 文件、计划、预览、标签 │
│ 固定宽度          │ 随左右 dock 状态伸缩               │ 可关闭、可调整宽度      │
└──────────────────┴─────────────────────────────────┴─────────────────────┘
```

最重要的布局结论：

1. 左侧导航是固定 dock，不覆盖 MainView。
2. 右侧面板是停靠式 split pane，不是 overlay。打开后会实际占用横向空间，MainView 变窄；关闭后 MainView 横向扩展。
3. 全局搜索、项目选择、模型选择、权限模式等才使用 overlay / popover；这些弹层会覆盖内容或压暗背景，但不会改变工作台的基础分栏关系。
4. Composer 是 MainView 内部的底部固定工作区。它不脱离 MainView 成为独立窗口；右侧面板打开时 Composer 会随 MainView 变窄。
5. 设置页复用了同一套应用外壳和左侧导航骨架，但右侧不再呈现会话流，而是滚动设置内容。设置内部采用「分类导航 + 页面内容 + 卡片/行控件」结构。

## 2. 调研方法与当前窗口

- 通过 macOS Computer Use 读取 ZCode 的可访问树，确认组件角色、文本、可操作性和当前状态。
- 通过窗口截图核对实际视觉关系，避免仅依赖无几何信息的可访问树。
- 对菜单、搜索面板、项目/分支/模型选择器、权限模式、上下文入口和右侧标签页搜索进行了可逆交互检查。
- 当前窗口约为 `1208 x 766`，深色主题，中文界面，当前工作区为 `Musefold`，Git 分支为 `main`。
- 当前工作区存在长会话和正在运行的 Agent 任务，因此 MainView 采样同时覆盖了空白新任务态和已有任务流态。

本文不把当前会话中的任务内容当作 ZCode 产品设计本身；任务文本、工具输出和代码 diff 只用于观察消息流组件的呈现方式。

## 3. 应用外壳

### 3.1 窗口层级

从外到内可以拆为：

1. macOS 原生窗口层：关闭、全屏、最小化按钮和系统菜单栏。
2. ZCode 根窗口：深色背景，内容区域有明显的圆角窗口内框。
3. 左右 dock 布局：左侧工作区导航、中央 MainView、可选右侧面板。
4. MainView 内部：顶部任务头部、滚动内容区、底部 Composer。
5. Modal / popover 层：全局搜索使用居中 modal；选择器使用锚定菜单；右侧标签页搜索使用右上角锚定 popover。

### 3.2 视觉基调

- 主色是近黑背景与深灰表面，层级主要靠明度差、细分隔线和轻微圆角表达。
- 文本分为高亮标题、正常正文、低对比度说明和状态辅助文本四级。
- 语义色承担状态表达：权限模式使用橙色强调，成功/启用状态使用绿色，图表使用蓝绿紫等多色，失败或警告在任务流中单独使用语义色。
- 视觉上不依赖大面积渐变或装饰插画。新任务页虽然有淡化的几何线稿标志，但主操作仍是 Composer。
- 常用控件的视觉形状偏紧凑：小圆角矩形、细边框、低高度行、图标砖和轻量徽标；没有把所有操作都做成大胶囊按钮。

### 3.3 近似几何

以下数值来自当前 `1208 x 766` 窗口截图，作为比例参考，不应当视为 ZCode 的公开设计 token：

| 区域 | 当前观测 |
|---|---|
| 左侧工作区 dock | 约 `255px`，打开和关闭右侧面板时保持不变 |
| MainView 顶部任务栏 | 约 `50px` 高，包含任务名、项目、分支和右侧工具入口 |
| 右侧工作面板 | 打开时约 `230-265px`，与 MainView 之间有垂直分隔线 |
| MainView Composer | 任务流态贴近底部；新任务态居中，宽度约 `640px` |
| 设置内容区 | 从左侧导航右边开始，内容最大宽度约 `800px`，两侧保留较大留白 |
| 设置导航 | 与工作区左侧 dock 同宽级别，约 `255px` |

## 4. 左侧工作区导航

左侧 dock 是整个应用的稳定锚点。它不随着当前任务滚动，也不因右侧面板开关改变宽度。

### 4.1 顶部窗口工具条

顶部从左到右可见：

- 工作区/应用入口图标。
- 后退与前进按钮；前进无历史时置灰。
- 一个绿色强调的快速入口按钮。
- 右侧的帮助、终端/面板等工具图标在不同页面出现。

这些按钮使用图标优先的窄控件，不占用项目导航的垂直空间。

### 4.2 一级操作区

当前工作区导航固定显示四个高频入口：

| 入口 | 视觉/行为 |
|---|---|
| 新建任务 | 左侧图标 + 文案，右侧显示 `⌘ N` |
| 搜索 | 左侧搜索图标 + 文案，右侧显示 `⌘ K` |
| 自动化 | 与任务管理同级，表示计划/自动运行能力 |
| 插件市场 | 与自动化同级，表示扩展能力入口 |

快捷键提示被放在行尾，不改变主文案的对齐。高频入口用统一行高和统一图标尺寸，避免每个功能看起来像独立产品。

### 4.3 视图切换行

项目区上方是一个紧凑控制带：

- `分组 / 项目` 是二段式 tab。
- 右侧有收起全部、筛选和排序、归档等操作。
- 选中 tab 使用浅灰背景块，未选中项保持低对比度文字。
- 控制带高度很小，说明它是视图控制，不是页面标题。

筛选和排序菜单包含两组互斥选项：

- 视图：按项目、时间线。
- 排序方式：更新时间、创建时间。

菜单以深灰小面板锚定在控制带下方，当前值在右侧使用勾选符号，不另起设置页。

### 4.4 项目视图

项目视图的组织方式是「项目组 → 任务列表」：

- 项目行使用文件夹图标、项目名和 hover 操作。
- 项目行可提供：更多、查看文件、新建任务。
- 项目下方直接显示任务标题和相对时间，例如「刚刚」「2小时」「1天」。
- 空项目不使用大型插画，而是显示紧凑的「暂无任务」。
- 项目区支持拖拽移动项目分区，应用树中将该区域暴露为 sortable。
- 任务 hover 后显示置顶任务、归档任务等上下文操作，静止状态只保留标题和时间，保持密度。

项目行的设计重点是「身份和动作分离」：静止时只让用户扫描项目名，动作只在 hover/focus 后出现，避免每行常驻三四个按钮造成噪音。

### 4.5 分组视图

分组视图去掉项目层级，改为任务的扁平可拖拽列表：

- 顶部操作从「收起全部」变为「新建分组」。
- 每行直接显示任务标题和相对时间。
- 每一项被暴露为 draggable，说明排序/移动是该视图的一等交互。
- MainView 和 Composer 不改变，只替换左侧数据组织方式。

这说明侧边栏是数据视图层，而不是 MainView 的业务容器：切换项目/分组不需要重建会话工作台。

### 4.6 底部固定区

左侧 dock 底部固定四类入口：

- `连接使用`：弹出界面主题、缩放、语言、使用统计、升级和连接使用菜单。
- 移动端远程控制：使用窄图标按钮呈现。
- 设置：进入完整设置工作区。
- 侧边栏宽度 splitter：可访问名称为「调整侧边栏宽度」。

底部入口与上方项目列表之间有明确的垂直空间隔离。列表滚动到底部时，账户/设置入口仍然可见。

## 5. MainView

### 5.1 新任务空白态

新任务页面的核心不是空状态说明，而是直接可输入的任务启动面：

1. 中央欢迎标题，例如「下午好呀，接下来交给我吧」。
2. Composer 上方的项目选择和 Git 分支选择。
3. 中央大 Composer，包含输入框和所有模型/权限控制。
4. 三条轻量提示建议：每周总结、终端错误分析、创建 PPT。
5. 一条订阅用户提示。
6. 底部三张可点击模板卡：Git 站会摘要、CI 失败与不稳定测试报告、自定义。

空白态将「开始工作」压缩为一条视觉路径：选择工作区/分支 → 输入目标 → 选择模板或直接发送。模板卡是辅助入口，没有与 Composer 争夺主层级。

### 5.2 已有任务流

已有任务的 MainView 由以下部件组成：

- 任务顶部标题栏：任务名、项目 pill、分支 pill、更多菜单。
- 右上角工具区：帮助、面板/终端、侧边栏开关等图标入口。
- 可滚动消息流：用户请求、Agent 回复、工具状态、文件读取、代码修改、计划/任务等。
- 回合状态行：`已工作 33 秒`、`正在压缩上下文` 等低对比度状态信息。
- 工具调用分组：终端、探索、文件更改等可以折叠，显示数量摘要。
- 文件变更/已读取条目：文件名、所在路径、变更数量和展开详情入口。
- Markdown 内容：标题、列表、行内代码、代码块和引用在同一消息流中混排。
- 消息级操作：复制、赞/踩、分叉、展开思考过程等。

消息流中的「工具分组」很关键：它把 Agent 的大量操作压缩成可扫描的摘要，只有需要排查时才展开详细命令或文件列表。

### 5.3 顶部任务头部

任务头部高度低、背景与 MainView 基本一致，不做独立大卡片。主要关系是横向排列：

```text
任务标题   [项目]   [分支]   [...]                         [工具] [面板]
```

项目和分支使用带图标的小型 pill，因为它们是当前上下文而非主要操作；标题保持普通文本，不使用超大字号。

### 5.4 消息视觉层级

- 用户消息通常以右对齐或右侧气泡表达，背景略亮于主背景。
- Agent 文本占据更大的内容宽度，以文档阅读方式呈现。
- 状态和工具摘要使用较小字号、低对比度颜色和图标，避免与 Agent 正文竞争。
- 代码/路径使用等宽或高对比度的 inline code 表达，文件名与路径分层呈现。
- 复制、分叉、反馈等操作保持在消息尾部，避免悬浮覆盖正文。
- 任务工作时，状态行与 Composer 之间保留稳定间距，Composer 不会被流式文本推走。

## 6. Composer 组件拆解

Composer 是 MainView 的核心操作组件，任务流态和新任务态共享同一套控制结构，只改变外部定位方式。

### 6.1 外框

- 深灰表面，细边框，约 `12-16px` 圆角。
- 新任务态居中且较窄，任务流态横向撑满 MainView 内容区并贴近底部。
- 高度稳定，不因模型名、权限名或 loading 文案变化而明显跳动。
- 输入区在上，控制栏在下；控制栏使用左右分布，左侧上下文，右侧模型/推理/发送。

### 6.2 输入区

空白状态 placeholder：`向 ZCode 提问，使用 @ 添加上下文，使用 / 选择命令或能力`。

输入区支持三种上下文入口：

- 添加附件。
- 使用 `@` 添加上下文。
- 使用 `/` 选择命令或能力。

这些入口通过加号按钮旁的「添加上下文」菜单暴露；菜单只有三项，层级浅，适合高频使用。

### 6.3 底部控制栏

从左到右：

1. 加号/上下文入口。
2. 权限模式：例如「完全访问」，橙色图标和文字，旁边有下拉箭头。
3. 模型供应商/模型选择：例如 `tvt-glm/glm-5.3`，使用 popover 进入供应商二级菜单。
4. 推理强度：例如「最高」，通常是 combo box。
5. 发送按钮或运行中的停止按钮。

运行中发送按钮替换成方形停止按钮；输入框仍保持可用，说明后续输入可以排队，而不是被运行态锁死。

### 6.4 Composer 菜单

#### 权限模式

菜单项是完整短语，而不是单独的 Allow/Deny：

- 变更前确认。
- 自动编辑。
- 计划模式。
- 完全访问。

每项附一行简短解释，当前项带 selected 状态。设计意图是让风险差异直接可读。

#### 模型选择

模型菜单第一层列供应商：`tvt-glm`、`tvt-gpt`、`tvt-claude`、`kimi`；当前供应商/模型带勾选；底部提供「管理模型」。

这是一个两级结构：供应商列表 → 具体模型。它避免把所有模型平铺在 Composer 中，同时将供应商管理与使用时选择分开。

#### 项目选择

项目菜单包含：

- 搜索工作区。
- 当前可用工作区列表。
- 打开文件夹。
- 远程连接。
- 不在项目中工作。

菜单同时承担「选择已有工作区」和「建立新工作区上下文」两种任务。

#### Git 分支选择

分支菜单包含：

- 搜索分支。
- 当前分支及未提交文件数。
- 创建并检出新分支。
- Git 图谱。

当前分支状态和未提交更改数量直接显示在选择器中，避免用户切分支前还要额外打开 Git 状态页。

## 7. 右侧工作面板与叠加关系

### 7.1 结构判断

右侧面板是 docked split pane，证据包括：

- MainView 与面板之间存在独立的垂直 splitter。
- 可访问树暴露「收起侧边面板」和「展开侧边面板」两个状态互斥按钮。
- 面板打开时，中央消息内容和底部 Composer 都在面板左侧结束，不被面板遮住。
- 面板关闭后，MainView 横向扩展到窗口右边，没有半透明遮罩、背景模糊或浮层阴影。
- 右侧面板本身拥有独立的标签页、搜索标签页、关闭标签页、新增标签和面板工具入口。

因此它不是「MainView 上方覆盖一张侧栏」，而是「MainView 与 side rail 同级的布局列」。

### 7.2 打开态布局

```text
左侧 dock 255px | MainView 约 60% | 垂直 splitter | Right rail 约 20%
```

右侧 rail 中可以出现：

- 计划/任务标签页。
- 文件或代码预览。
- 终端、浏览器、审查等辅助工作面板。
- 右上角的标签页搜索与最近关闭标签页。

右侧面板内部的内容可独立滚动。它的操作不会把消息流推到另一个路由，而是把辅助工作保持在当前任务旁边。

### 7.3 关闭态布局

关闭后：

- MainView 占据左侧 dock 之外的全部剩余宽度。
- Composer 变宽，内容输入区与底部控制栏随之扩展。
- 右侧只保留一个很小的展开入口/抓手，不保留面板内容。
- 不出现背景遮罩或 modal focus trap。

这套设计适合需要边看会话边对照代码的 Agent 工作流，也适合在阅读长答案时临时释放宽度。

### 7.4 右侧标签页搜索

标签页搜索是右上角锚定 popover，不是全局 modal：

- 上半区列出打开的标签页。
- 每一项显示标签名、时间/状态和关闭按钮。
- 下半区列出最近关闭的标签页。
- 搜索输入位于 popover 顶部。

它只影响右侧 rail 的标签页选择，不会压暗 MainView，也不会阻断 Composer。

### 7.5 与左侧 dock 的关系

左侧 dock 和右侧 rail 的职责完全不同：

| 维度 | 左侧 dock | 右侧 rail |
|---|---|---|
| 作用 | 导航、工作区、任务组织、设置入口 | 当前任务的辅助工作内容 |
| 稳定性 | 应用级固定 | 会话级可选 |
| 是否滚动 | 项目/任务列表滚动，底部工具固定 | 面板内容和标签页独立滚动 |
| 关闭后 | 通常仍保留 | MainView 释放空间 |
| 是否 overlay | 否 | 否 |
| 状态持久化倾向 | 高 | 与当前任务/标签页关联 |

## 8. 全局搜索与其他 overlay

### 8.1 命令中心

全局搜索/命令中心通过 `搜索 ⌘ K` 打开：

- 整个工作台被黑色半透明层和模糊效果压暗。
- 中央出现约 `490px` 宽的圆角深灰面板。
- 顶部是搜索输入。
- 下方是范围 tab：全部、操作、任务、文件。
- 内容按最近任务、建议、面板、配置、应用等分组。
- 建议行右侧显示快捷键，例如 `⌘ N`、`⌘ O`、`⌘ B`、`⌘ J`。

这是应用中少数真正的 modal overlay。它的目标是跨区域导航，因此使用全局遮罩和集中焦点。

### 8.2 轻量 popover 的共同规则

项目、分支、模型、权限、上下文、连接使用菜单都遵循同一套规则：

- 锚定在触发控件附近。
- 深灰背景、细边框、较小圆角。
- 选中项使用勾选或 selected 背景。
- 选项数量少，通常一层或两层。
- Esc 关闭，不影响当前 MainView 内容。

这形成了清晰的 overlay 分级：跨区域搜索用 modal，局部选择用 popover，辅助内容用 dock。

## 9. 设置工作区

### 9.1 设置外壳

点击左侧底部设置后，应用切换到独立设置工作区：

- 左侧保留设置导航，不显示项目任务列表。
- 顶部有「返回工作区」。
- 设置导航按「基础设置」「Agent 能力」「数据与统计」分组。
- 当前项使用浅灰选中背景和小型图标。
- 内容区从导航右侧开始，保留较大的左右留白，页面标题约 `28-32px`。
- 右上角保留帮助入口；底部仍保留连接使用和账户入口。

设置导航项完整清单：

| 分组 | 页面 |
|---|---|
| 基础设置 | 常规、外观、模型设置、浏览器 |
| Agent 能力 | 记忆、子智能体、插件、MCP 服务器、技能、命令、钩子 |
| 数据与统计 | 索引库、使用统计、引导 |

### 9.2 通用设置页面骨架

常规、外观等表单页使用统一的 section/card 结构：

```text
页面标题
页面副标题或当前状态徽标

设置分组标题
┌────────────────────────────────────────────┐
│ 左：设置名                                  │
│ 左：解释文字                          右：控件 │
├────────────────────────────────────────────┤
│ 左：设置名                                  │
│ 左：解释文字                          右：控件 │
└────────────────────────────────────────────┘
```

具体特征：

- 分组卡片是深灰表面，行之间使用细分隔线。
- 标签和说明在左，开关、下拉、stepper、输入框和保存按钮在右。
- 说明文字允许多行，但控件列保持右对齐。
- 设置页是长页面，右侧有独立滚动条；滚动不会移动左侧导航。
- 需要重启的设置在说明文案中直接解释生效时机。
- 保存按钮在输入行右侧，未发生变更时置灰。

### 9.3 常规

常规页是最长的单栏表单，按功能分成：

- 界面语言。
- 继承系统终端 Profile、终端字体、增强 Find/Grep。
- HTTP 代理、不使用代理的地址、自定义证书。
- Chrome 硬件加速、预览版更新、自动下载更新。
- 任务通知、通知声音、保持电脑运行。
- 交互行为：队列、提问自动继续、完整保留模型 I/O。
- 消息流展示：显示思考过程、显示待办、分组探索工具、分组终端命令、分组文件更改。
- 自动归档旧任务和归档保留时长。
- 数据存储路径、引导、优化体验。

设计上将「纯 UI 偏好」「网络/运行时配置」「Agent 消息流行为」放在同一页面内，用分组卡片和长滚动解决信息量问题，而不是再套多级子页面。

### 9.4 外观

外观页将主题类设置与代码显示设置分开：

- 界面主题：浅色、深色、跟随系统。
- 界面字号：stepper，说明图标和布局尺寸不随之改变。
- 浅色代码主题、深色代码主题。
- 显示行号、长行自动换行。
- 代码字号。
- 浅色/深色代码预览，当前生效主题有状态标记。

外观页的代码预览卡片是一个可视化验证区域：用户可以直接看到主题、行号和字号设置的效果，而不是只在下拉框里选择名称。

### 9.5 模型设置

模型设置是设置工作区中最明显的 master-detail 页面：

- 左侧供应商列表约 `215-240px`，有「智谱」「自定义供应商」分组。
- 供应商行包含品牌/方块图标、名称、启用状态点。
- 右侧详情标题包含供应商品牌、启用/未启用徽标和连接方式下拉。
- 当前采样中的详情是 BigModel，顶部先显示连接状态，再显示连接按钮。
- 下面是编程套餐、体验套餐、个人套餐、团队套餐等可选卡片。
- 方案卡片使用绿色、蓝色、蓝绿色等语义/商业强调色，卡片右侧有箭头。

该页面体现了 ZCode 的一个重要策略：当实体数量较多、详情较长时，列表和详情同时保留在一个页面，不用「列表页 → 编辑弹窗 → 再返回」的跳转链。

### 9.6 记忆

记忆页是「开关 + 文件浏览」结构：

- 顶部是工作区记忆总开关和成本说明。
- 下方是工作区选择器、记忆数量和搜索记忆文件输入框。
- 文件列表使用一组统一的深灰行，每行有记忆文件图标、文件名、更新时间。
- 每行右侧提供在 Finder 中打开和打开方式菜单。
- 空间利用率较高，但文件行的主信息仍保持明确的两行结构。

### 9.7 插件

插件页使用页内 tab：`插件 7 / MCP 4 / 技能 14`。

通用结构：

- 顶部页标题、tab、搜索框。
- 已安装区：刷新、新建；没有安装项时显示虚线边框空态和「浏览插件」按钮。
- 内置区：每个插件是一行，左侧图标，中间名称和描述，右侧更多菜单和开关。
- 列表行按功能分组，行高稳定，长描述使用截断。

插件页更接近管理列表，不使用复杂卡片网格；状态动作优先放在行尾。

### 9.8 MCP 服务器

MCP 页与插件页复用列表模板，但增加作用域选择：

- 顶部有用户作用域 popover。
- 搜索 MCP 服务器。
- 已安装区显示服务器名、transport/启动命令和启用开关。
- 插件区列出由插件提供的 MCP，并用「插件」徽标说明不能独立编辑。
- 已安装项和插件项使用不同的区块标题，避免误以为两类对象拥有相同生命周期。

### 9.9 技能、命令、钩子

这三页共享「扩展资源列表」骨架：

- 作用域选择器：用户。
- 当前资源数量。
- 搜索框。
- 已安装数量。
- 刷新、新建、更多操作。
- 空态引导。
- 分组资源列表；每行显示图标、名称、描述和启用开关。

差异只在资源类型和空态文案：

- 技能按插件/文档能力分组。
- 命令使用命令行图标和斜杠命令名。
- 钩子在空态时说明它会在任务生命周期事件中运行命令。

这种模板化让用户可以预测不同扩展资源页的使用方式，降低 Agent 配置的学习成本。

### 9.10 使用统计

使用统计页是数据密度最高的页面：

- 标题旁有「应用用量」状态徽标。
- 顶部 KPI 横条：累计 Token、峰值 Token、最长聊天时长、当前连续天数、最长连续天数。
- Token 活动使用日历热力格，支持每日/每周/累计 tab。
- 时间范围使用近 7 日/近 30 日切换。
- 下方是每日 Token 趋势图，按模型使用颜色图例。

KPI 用一行五列做第一层摘要，图表负责第二层趋势分析；页面没有把每个统计指标做成独立大卡片，保持了运营面板的扫描效率。

## 11. 设计规律与可复用原则

### 11.1 dock、popover、modal 的边界清楚

- dock：持续存在、承载工作内容、占布局空间。
- popover：由一个控件触发、局部选择、关闭后回到原上下文。
- modal：跨区域搜索或高影响操作、需要遮罩和集中焦点。

这是 ZCode 最值得复用的交互分层。若把右侧文件/计划面板错误实现为覆盖层，用户会失去「边读 Agent 消息边对照文件」的空间关系；若把模型选择做成 modal，则会让高频切换过重。

### 11.2 常驻信息做摘要，详情按需展开

项目列表只显示标题/时间，工具调用只显示分组摘要，标签页只显示名称/时间；详细命令、文件、思考过程和最近关闭标签页都通过展开或搜索访问。

### 11.3 运行状态是结构化状态，不是单独 toast

「已工作」「思考过程」「探索」「终端」「更改」都出现在消息流结构中，并且有计时、数量、展开/收起和停止状态。这比把 Agent 状态全部放在右下角 toast 更适合长任务。

### 11.4 设置页和工作台共享视觉语法

左侧导航、深色表面、细分隔线、紧凑圆角、图标砖、状态点和右侧操作对齐方式在工作区与设置页之间保持一致。设置页换了信息架构，但没有换一套产品风格。

### 11.5 高频选择器优先两级而不是平铺

模型按供应商再按具体模型，项目按工作区再按分支，扩展资源按类型再按列表。每级都提供搜索或管理入口，避免单个菜单变成长列表。

## 12. 对 Musefold 的映射建议

以下建议只基于本次 UI 调研，不替代 Musefold 现有产品规格：

1. 保持左侧产品导航与右侧辅助面板职责分离。生图工作台中的历史/方案/参数辅助内容适合使用 dock，不应覆盖主画布或提示词区。
2. Composer 可以复用「输入区上方、策略/上下文在左、模型/参数/执行在右」的横向控制栏，但图像生成参数应以任务域实际需要为准，避免把所有设置都塞进底栏。
3. 运行中的生图任务应沿用消息流的结构化状态：阶段、数量、错误、重试和输出摘要都应可展开，而不是只显示一个 loading 圆环。
4. 设置中的 master-detail 模式适合 Provider、模型、账号连接等「列表多、详情长、需要频繁切换」的对象；短设置仍可用分组卡片。
5. 右侧 rail 打开/关闭必须真正改变 MainView 的可用宽度，并且 Composer 与内容区使用同一个布局列；不能只在视觉上叠加一层半透明面板。
6. 全局搜索、局部选择器和工作面板需要三种不同的焦点与退出协议，尤其要保留 Esc 关闭 popover/modal 而不触发业务动作。
7. 资源管理列表可抽象为同一套「作用域 + 搜索 + 计数 + 刷新/新建 + 分组行」，再由 Provider、模型、技能和 MCP 通过数据差异复用。

## 13. 验证边界

- 本文观察的是当前 macOS 桌面构建和当前深色主题。
- 没有把设置中的每一个深层弹窗、首次启动引导和错误状态逐一打开；这些页面的共性结构已从可访问树和代表性截图确认。
- 没有验证 Windows/Linux 原生窗口按钮和布局差异。
- 没有验证窄窗口或移动端断点；当前结论主要适用于桌面宽窗口。
- 本文没有修改 ZCode 安装包、Musefold 源码或现有用户变更。
