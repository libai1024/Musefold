# 02. MainView、任务流与 Composer

## 1. MainView 的职责

MainView 是 ZCode 的主要工作区，不是普通聊天页。它同时呈现任务上下文、Agent 运行过程、工具调用、文件改动和下一次输入。因此布局要保持一条连续的纵向阅读路径：

```text
MainView
├── task header                 当前任务身份和操作
├── message stream              用户消息、Agent 消息、工具过程
│   ├── markdown response
│   ├── thinking / work status
│   ├── tool group
│   ├── file link / diff summary
│   └── message actions
└── Composer                    输入、权限、模型、发送/停止
```

MainView 的宽度由外壳剩余空间决定；右侧 dock 打开时它会收窄，Composer 的外框、文本区域和工具栏同步收窄。MainView 不应被右侧 dock 覆盖。

## 2. 新建任务页面

没有选中已有任务时，中央区域显示新建任务欢迎页。观察到的主要结构如下：

```text
                 下午好呀，接下来交给我吧

                 ┌─────────────────────────────┐
                 │ Musefold   main             │
                 │ 向 ZCode 提问...             │
                 │ +  完全访问  模型  极高  发送 │
                 └─────────────────────────────┘

          建议/快捷操作
       ┌──────────┐ ┌──────────┐ ┌──────────┐
       │ Git 站会摘要 │ CI 失败报告 │ 自定义   │
       └──────────┘ └──────────┘ └──────────┘
```

### 2.1 欢迎内容

- 主文案：`下午好呀，接下来交给我吧`，居中、字号大于普通正文。
- 下方是 Composer，项目 pill 显示 `Musefold`，分支 pill 显示 `main`。
- Composer 下方提供建议或模板卡片。
- 观察到的模板：`Git 站会摘要`、`CI 失败与不稳定测试报告`、`自定义`。

模板卡片的作用是把常用任务转成可点击的初始 prompt。它们不是营销卡片，不应占据首屏大面积空间；卡片应保持短标题、简短说明和稳定高度。

### 2.2 新建任务上的按钮

| 控件 | 形式 | 行为 |
| --- | --- | --- |
| 项目 pill | 选择器 | 打开工作区选择器 |
| 分支 pill | 选择器 | 打开分支选择器 |
| 添加上下文 `+` | 图标按钮 | 打开附件、@ 上下文、/ 命令菜单 |
| 权限 `完全访问` | 选择器 | 打开权限/模式菜单 |
| 模型名称 | 选择器 | 打开供应商与模型菜单 |
| 推理等级 `极高`/`最高` | 选择器 | 调整推理强度或模型参数 |
| 发送 | 图标按钮或文字+图标 | 创建任务并提交输入 |
| 模板卡片 | 卡片按钮 | 将模板填入或直接开始对应任务 |

## 3. 已有任务的任务头

已有任务页顶部是一个横向 task header，位置固定在消息流上方。它包含：

- 当前任务标题：主身份信息，过长省略。
- 项目 pill：显示 `Musefold`。
- 分支 pill：显示 `main`，必要时附带未提交状态。
- 更多按钮：任务级菜单。
- 右侧工具按钮：与面板、布局或任务操作有关的图标入口。

建议的结构关系：

```text
┌──────────────────────────────────────────────────────────────┐
│ 任务标题  [Musefold] [main]                         [工具][⋯] │
└──────────────────────────────────────────────────────────────┘
```

任务头只保留当前任务的身份和高频操作。删除、归档、导出等低频动作放到更多菜单，避免任务头变成一串图标。

## 4. 消息流

### 4.1 用户消息

用户消息靠近右侧或以右对齐气泡/块状内容显示，与 Agent 响应形成方向差异。消息块包含：

- 用户输入正文。
- 可能的附件或上下文 chip。
- 时间或运行状态（如果当前模式显示）。
- hover 后的复制、编辑、重新运行或更多动作。

气泡不宜过宽，应保留中央阅读线；长代码和长 prompt 应使用可滚动或折叠处理。

### 4.2 Agent 消息

Agent 内容靠近主内容列，使用 markdown 排版：

- 段落、标题、列表和引用。
- 代码块及语言标记。
- 文件路径链接。
- diff 摘要或变更列表。
- 复制、反馈和 fork 等消息操作。

Agent 消息不应被强制放进卡片。只有工具调用、代码块、diff 和需要边界的结构使用局部容器；正文保持开放的阅读面。

### 4.3 工作状态

任务执行中会显示类似 `已工作 ...` 的时间/状态信息，并可以展开 `思考过程`。状态组件的重点是让用户知道 Agent 是否仍在运行、正在做什么，以及是否可以继续输入。

推荐把状态分为：

| 状态 | 视觉表达 | 可用动作 |
| --- | --- | --- |
| idle | 无状态条或简短提示 | 发送新输入 |
| working | spinner/动态状态文字 | 停止运行 |
| waiting confirmation | 强调提示 | 确认、拒绝或变更权限 |
| completed | 完成标记、耗时摘要 | 复制、反馈、fork、继续任务 |
| failed | 错误色、错误说明 | 重试、复制错误、查看日志 |

### 4.4 思考过程

`思考过程`是可折叠的次级信息。默认应比最终回答弱，展开后再显示详细过程或阶段状态。折叠按钮需要有明确的展开/收起箭头和可访问名称，不要只依赖旋转动画表达状态。

## 5. 工具调用组

观察到工具过程以分组形式出现：

- `Explore`：探索文件、检索项目结构或读取上下文。
- `Terminal`：命令执行。
- `Changes`：文件变更、diff 或修改结果。

工具组的布局：

```text
┌──────────────────────────────────────────┐
│ [icon] Explore                    [⌄]    │
│        查找相关文件                       │
│        file path / result                 │
├──────────────────────────────────────────┤
│ [icon] Terminal                   [⌄]    │
│        npm run ...                        │
│        output                             │
└──────────────────────────────────────────┘
```

### 5.1 工具组控件

| 控件 | 默认 | 打开/完成状态 |
| --- | --- | --- |
| 工具图标 | 表示工具类型 | 运行中可显示动态状态 |
| 工具名称 | `Explore`、`Terminal`、`Changes` | 作为组标题，支持折叠 |
| 折叠箭头 | 指向当前状态 | 展开显示输入和输出 |
| 命令/查询摘要 | 次级文本 | 过长截断，展开后看完整内容 |
| 输出区 | 等宽字体或轻量容器 | 可滚动、可复制 |
| 文件链接 | 链接文本 | 点击打开文件或右侧上下文 |
| diff 摘要 | 增删统计/文件名 | 点击查看具体变更 |

工具组应是“局部边界”，而不是包住整条消息流的大卡片。多个连续工具调用可以共享一个组容器，但组之间要有清晰的垂直间距。

## 6. 消息操作按钮

在 Agent 消息或工具结果附近观察到：

- 复制：复制正文、命令或代码。
- 反馈：正向/负向反馈或打开反馈菜单。
- Fork：从当前消息分叉新的任务路径。
- 更多：低频操作。
- 文件/路径链接：打开文件或同步到右侧面板。

这些通常是 hover 才出现的图标按钮，以减少阅读噪音。按钮必须保留至少 28-32 px 的稳定 hit area；图标本身可以小，但可点击区域不能跟着图标缩小。

## 7. Composer 结构

Composer 是 MainView 底部的固定输入单元。观察到的形态是深色、圆角、带边框的外框，包含文本输入区和底部控制行：

```text
┌─────────────────────────────────────────────────────────────┐
│ 向 ZCode 提问，使用 @ 添加上下文，使用 / 选择命令或能力。     │
│                                                               │
│ [＋] [完全访问 ▾]                         [模型 ▾] [极高 ▾] [发送] │
└─────────────────────────────────────────────────────────────┘
```

### 7.1 输入区

- placeholder：`向 ZCode 提问，使用 @ 添加上下文，使用 / 选择命令或能力`。
- 多行输入，内容增多时在固定最大高度内滚动。
- focus 时外框、光标和 placeholder 对比度提高。
- 使用 `@` 与 `/` 时可以打开对应的上下文/命令选择。
- 输入为空时发送按钮 disabled 或保持低对比度。
- 运行中时发送按钮切换为停止按钮，通常使用实心方形图标。

### 7.2 底部控制行

| 控件 | 菜单内容/行为 | 视觉重点 |
| --- | --- | --- |
| `+` 添加上下文 | 添加附件、使用 `@` 添加上下文、使用 `/` 选择命令或能力 | 图标按钮，打开左下/近端菜单 |
| `完全访问` | 变更前确认、自动编辑、计划模式、完全访问 | 橙色或强调色，表示权限影响 |
| 模型选择 | tvt-glm、tvt-gpt、tvt-claude、kimi，以及管理模型 | 选择器，显示当前模型 |
| `极高`/`最高` | 推理等级或模式 | 紧凑选择器，不与模型混成一项 |
| 发送/停止 | 提交或中止任务 | 运行中必须明确可停止 |

底部控制行把“任务权限”和“模型能力”放在同一工作单元内，但使用不同视觉语义：权限强调风险，模型和推理强调配置。

## 8. Composer 菜单细节

### 8.1 添加上下文菜单

菜单项：

- `添加附件`
- `使用 @ 添加上下文`
- `使用 / 选择命令或能力`

它们应该是带图标的三行菜单，每行包含主标签和可选说明。菜单从 `+` 按钮附近展开，不能遮住输入文本的可编辑区域。

### 8.2 权限菜单

权限菜单包含四个模式，每个模式带名称和描述：

- `变更前确认`：任何写入或高影响动作先询问。
- `自动编辑`：允许一定范围内的自动修改。
- `计划模式`：先生成计划或只读分析。
- `完全访问`：允许更广泛的工作区操作。

当前选中模式需要 check、选中背景或明显的颜色标记。危险模式不能只靠颜色，文字描述必须仍然可读。

### 8.3 模型菜单

第一层按供应商/模型分组：

- `tvt-glm`
- `tvt-gpt`
- `tvt-claude`
- `kimi`
- `管理模型`

模型菜单的行要区分供应商、模型名、可用状态和当前 check。管理模型是导航动作，应放在分隔线后的尾部。

## 9. MainView 与右侧面板的叠加方式

### 9.1 结论

右侧面板是独立 docked split pane：

```text
打开状态
┌──────────────┬───────────────────────────┬──────────────┐
│ left sidebar │ MainView                  │ right panel  │
│              │ header / stream / composer │ tabs/content │
└──────────────┴───────────────────────────┴──────────────┘

关闭状态
┌──────────────┬─────────────────────────────────────────┐
│ left sidebar │ MainView                                │
│              │ header / stream / composer               │
└──────────────┴─────────────────────────────────────────┘
```

它不是从右边盖住 MainView 的 overlay drawer：

- 没有全屏遮罩。
- MainView 内容区域实际变窄。
- Composer 的外框和文本宽度一起变窄。
- 右侧面板有竖向分隔条，可表达边界或拖拽。
- 有 `收起侧边面板` 和 `展开侧边面板` 两种控制状态。

### 9.2 右侧面板内容

面板顶部是标签/工具条，典型标签包含：

- 文件或工作区上下文。
- 终端。
- 变更/Changes。
- 浏览器或其他插件面板。

标签栏应固定在面板顶部，内容区独立滚动。标签按钮使用 selected indicator，而不是给每个标签做大圆角卡片。

### 9.3 右侧标签搜索

标签栏提供搜索入口时，搜索结果以右上角锚定的 popover 展开：

- 显示已打开标签。
- 显示最近关闭标签。
- 支持输入过滤。
- 不遮罩 MainView。
- 关闭后恢复原标签焦点。

这说明“面板本体”和“面板内的搜索”是两个层级，不能把搜索做成一个会重新计算三栏宽度的大页面。

## 10. MainView 状态矩阵

| 状态 | 任务头 | 消息区 | Composer | 右侧面板 |
| --- | --- | --- | --- | --- |
| 新任务 | 欢迎文案/项目/分支 | 建议模板 | 可编辑 | 默认可关闭或空 |
| 空任务 | 标题已生成 | 空状态或提示 | 可编辑 | 可选 |
| 运行中 | 显示运行标记 | 工具组持续追加 | 停止按钮 | 可查看实时上下文 |
| 等待确认 | 显示等待提示 | 权限请求或计划 | 确认/拒绝 | 可查看相关文件 |
| 已完成 | 显示耗时/完成 | 最终回答和操作 | 可继续输入 | 可查看变更 |
| 失败 | 错误状态 | 错误信息 | 重试/继续 | 日志或诊断 |

## 11. 复刻验收清单

- [ ] 新建任务欢迎内容在中央纵向居中，模板卡片不抢过 Composer。
- [ ] 已有任务的 task header 始终能看到项目和分支上下文。
- [ ] 消息流可滚动，Composer 不随消息滚走。
- [ ] 工具组可以折叠，长输出不撑爆布局。
- [ ] 文件链接、diff 摘要、复制、反馈、fork 均有明确 hit area。
- [ ] Composer 的权限、模型、推理和发送/停止状态彼此独立。
- [ ] 右侧 dock 打开后 MainView 真实变窄，不出现覆盖和遮挡。
- [ ] 右侧标签搜索是局部 popover，不使用全屏遮罩。
- [ ] 运行中、等待确认、失败状态都能在不依赖颜色的情况下被识别。
