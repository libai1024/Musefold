# Musefold / 未像 v0.3.2 方案 UI 与交互规范

> 文档状态：交互设计已确认，待实现  
> 版本：`v0.3.2`  
> 事实源范围：方案中心、方案详情、Composer 调用、创建、试运行、历史提取和 GitHub 识别  
> 关联文档：[设计方案规范](V03.2-DESIGN-SCHEME-SPEC.md) · [Agent Runtime 开发规范](V03.2-AGENT-RUNTIME-DEVELOPMENT.md)

## 1. 核心产品模型

### 1.1 方案就是 Musefold 中可调用的 Skill

Musefold 不再建立“方案包含 Skill”的第二层产品对象。数据、运行时和分享边界统一为 Skill；中文产品界面统一称为“方案”。

- 从 GitHub 添加 Skill：形成一个方案草稿。
- 从历史图片、历史对话、提示词或用户想法创建：Agent 生成一个本地 Skill，并以方案呈现。
- 多个来源需要组合时：编译为一个新的组合 Skill，用户仍只调用一个方案。
- 技术详情可以出现 `Skill`、仓库、commit、文件和依赖；普通界面不要求用户理解这些概念。
- Musefold 只接纳能够安全转换为视觉生成或编辑能力的 Skill。其他仓库只能作为创建来源，不能伪装成可运行方案。

产品中的三个职责边界为：

```text
方案中心 -> 发现、添加和管理
方案详情 -> 理解效果、来源和输入要求
Composer -> 创建、使用、试运行和修改
```

不建立独立 Skills 页面，不建立方案包管理器，不把结构化字段编辑器作为普通用户的主入口。

### 1.2 品牌原则

- 界面应像一张安静、可靠的创作桌，不像开发者包管理器或在线图片社区。
- 真实生成结果是方案价值的主要证据；图标、标签和营销文案不能替代示例图。
- Ember 橙只用于识别中、待处理、焦点和主动作；不用于大面积背景或装饰。
- 页面使用瓷白、石墨文字、实色层级、薄分隔和低阴影，不使用渐变、光晕和卡片瀑布流。
- 用户始终能看到 Agent 正在采用的来源和提取意图，不在后台静默增加创作规则。

## 2. 状态与版本

### 2.1 用户可见状态

方案只显示两个状态：

| 状态 | 含义 | Composer 可引用 | 主要动作 |
|---|---|---:|---|
| `draft` / 草稿 | 尚未完成本机试运行，或正式方案存在待验证的新版本 | 否 | 继续、试运行 |
| `formal` / 正式 | 已完成至少一次本机成功试运行并由用户确认 | 是 | 使用 |

`试运行` 是运行模式，不是第三种方案状态；`发布` 保留给未来公开市场，不用于本地方案转正。

### 2.2 状态流转

```text
添加 Skill / Agent 创建
          ↓
        草稿
          ↓
      本机试运行
          ↓
    用户选择或确认封面
          ↓
       设为正式
```

- 仓库自带示例不能替代本机试运行。
- 试运行成功不自动转为正式，必须由用户确认。
- 正式方案被修改或上游 Skill 更新时，现有正式版本继续可用，同时创建新的草稿版本。
- 新草稿完成试运行并确认后，才替换当前正式版本。
- 第一版不把创建或修改过程接入普通聊天历史；草稿保存在“我的方案”，点击“继续”恢复工作状态。

### 2.3 转为正式的最低条件

1. 有名称和简短说明。
2. 明确用户必须提供的输入。
3. 至少一次成功的本机试运行。
4. 至少一张有效封面图。

## 3. 方案中心

### 3.1 页面结构

顶部应用标题栏显示“方案”，内容区不重复页面标题和说明文案。

```text
方案                                      [刷新] [新建 v]

[我的方案] [发现]

[搜索方案________________________________]

草稿
[缩略图] 方案名称      [缩略图] 方案名称
         来源 · 草稿             来源 · 草稿
         等待试运行    继续       等待试运行    试运行

正式
[缩略图] 方案名称      [缩略图] 方案名称
         来源 · 正式             来源 · 正式
         4 张示例       使用       3 张示例       使用
```

### 3.2 布局规则

- 内容最大宽度 `960px`，水平居中。
- 宽屏两列，窄窗口单列；不提供手动视图切换。
- 单个列表项稳定高度约 `72px`，缩略图 `56 x 56px`。
- 缩略图使用 `object-fit: contain`，不得裁切方案作品。
- 列表项默认无外框，悬停时使用浅瓷灰实色背景；不增加阴影卡片。
- `草稿` 仅在存在内容时显示，并位于正式方案上方；草稿按最近修改排序。
- 正式方案默认按最近使用排序。
- 状态使用次级文字，不使用彩色胶囊。需要处理的草稿可以显示 Ember 小点。
- 行尾只显示一个主要动作，其他操作进入 `...` 菜单。
- 搜索匹配名称、说明、作者和 GitHub 仓库。

### 3.3 按钮状态

| 对象状态 | 行尾按钮 |
|---|---|
| 发现页、尚未添加 | 添加 |
| 已添加、尚未验证 | 试运行 |
| 已有草稿创建过程 | 继续 |
| 正式 | 使用 |
| 正式且有新草稿版本 | 使用；“继续处理草稿”放入详情或菜单 |

点击整行进入详情；点击行尾按钮只执行动作，不额外跳转详情。

### 3.4 新建菜单

```text
从一个想法开始
从 GitHub 添加
从历史内容创建
从提示词创建
```

四个入口进入同一个 Composer 创建体验，只预先附加不同来源。

## 4. 方案详情

### 4.1 页面结构

```text
方案 > 留白杂志海报

[图标] 留白杂志海报
       将照片展开成留白充足的纸张海报
       Skill · LiamGvchi/gc-minimal-zine-poster

                                      [...] [使用]

                 [折叠相册]

适合制作
需要提供
来源与版本
技术详情 >
```

- 内容最大宽度 `880px`。
- 不使用外层卡片；各部分使用间距和细分隔组织。
- 主按钮按状态显示“添加”“试运行”或“使用”。
- 普通信息优先回答：能做什么、需要什么、能得到什么、来自哪里。
- Skill 文件、依赖、权限、commit 和兼容 Provider 收入折叠的“技术详情”。

### 4.2 操作菜单

正式方案：

```text
在 Composer 中修改
查看来源
导出方案
检查更新
移除方案
```

草稿：

```text
重命名
查看来源
删除草稿
```

危险操作放在菜单底部，并与普通操作分隔。

## 5. 折叠相册与封面

### 5.1 组件行为

- 当前图片完整显示在最前方，使用 `contain`，不得裁切。
- 后方最多露出三张图片，每层向右、向下错开约 `6px`；不旋转，不使用装饰性阴影。
- 点击后层图片，只把它切换到最前方查看，不修改永久封面。
- 点击当前最前方图片，打开全屏查看。
- 非封面图片位于前方时，显示“设为封面”。
- 支持左右方向键、触控滑动和明确的前后按钮。
- 动画约 `200ms`，只使用位移和透明度；减少动态效果时即时切换。
- 左下角标记“仓库示例”或“本机生成”，右下角显示当前序号和总数。
- 只有一张图片时退化为单图查看器，不制造虚假叠层。
- 详情相册最多突出展示封面和四张示例；更多关联结果进入完整结果列表。

### 5.2 图片来源与封面规则

- Skill 来源方案优先展示可信仓库示例，也可以使用本机生成结果作为封面。
- Musefold 创建的方案只能使用该方案关联的试运行或正式运行结果作为封面。
- 普通上传图片不能直接设为方案封面。
- 首次成功试运行结果自动加入相册，但用户可以移除。
- 仓库示例必须标记“仓库示例”；本地运行结果必须标记“本机生成”。
- 没有示例时允许保存草稿；设为正式前必须存在成功的本机试运行图片和封面。

## 6. Composer 附件栏

### 6.1 基本结构

方案位于 Composer 上方附件栏的第一位，参考图依次排在后方：

```text
[方案图标 留白杂志海报 x] [主图] [风格参考]
```

- 一次对话只允许一个主方案。
- 多 Skill 能力必须先编译为一个组合方案，不在 Composer 中堆叠。
- 点击方案附件打开轻量浮层：摘要、来源、输入要求、查看详情、更换和移除。
- 选择另一个正式方案时直接替换，并显示可撤销提示。
- 草稿不出现在普通方案选择器中。

### 6.2 方案选择器

方案选择器锚定在 Composer 上方，不打开阻塞式全屏弹窗：

```text
选择方案
[搜索我的方案________________]

最近使用
[缩略图] 方案名称

我的方案
[缩略图] 方案名称

                              浏览全部方案
```

- 最近使用最多四项。
- 支持方向键、回车、Esc 和可见焦点。
- 小面板只显示本地正式方案；“浏览全部方案”进入方案中心。
- 搜索无结果时提供“前往发现”，不在小面板内加载远程市场列表。

### 6.3 必需图片输入

方案声明的图片槽位使用具名附件位置：

```text
[留白杂志海报 x] [+ 主图 · 必需] [+ 风格参考 · 可选]
```

优先使用方案定义的名称；没有定义时才使用“图 1”“图 2”。缺少必需图片时禁止发送，并把焦点移动到第一个缺失位置；可选图片不主动打扰。

## 7. Composer 变量节点

### 7.1 表现形式

非图片输入使用结构化 `@变量名` 节点，不要求用户维护结束符：

```text
@标题     夏日松弛感
@副文案   留白，让风经过

整体再克制一些，减少装饰元素。
```

- `@变量名` 不可被改名，后方值可以直接编辑。
- 必填变量自动出现；可选变量默认隐藏，通过输入 `@` 或 `+` 添加。
- `Tab` 在必填变量之间移动。
- 粘贴 `@变量名 内容@` 时可以识别并转换为结构化节点。
- 删除必填变量的值不会删除节点；可选变量可以整体移除。
- 必填值为空时显示 Ember 小点或细下划线，发送时聚焦第一个空项。
- 长值自动展开为多行，不把 Composer 撑成多层卡片。

### 7.2 类型映射

| Skill 输入类型 | Composer 控件 |
|---|---|
| 短文本 | 单行变量值 |
| 长文案 | 多行变量值 |
| 选项 | 变量值菜单 |
| 数字 | 输入或步进器 |
| 颜色 | 色块和颜色名称 |
| 图片 | 附件栏图片槽位 |
| 比例、数量、Provider | Composer 原有专用控件，不转为普通变量 |

Agent 可以从自由文字中识别变量值，并短暂标记“已从输入识别”。用户继续发送即视为接受，也可以先修改；系统不得静默删除用户原文。

## 8. Composer 三种模式

### 8.1 使用正式方案

- 从详情点击“使用”始终开启新对话并附加正式方案。
- 从当前 Composer 选择方案则附加到当前对话。
- 方案附件使用普通石墨色；变量和图片槽位自动准备。
- 用户自由输入只影响本次运行。
- 每次结果保存方案 revision、来源和优先级快照。

### 8.2 试运行草稿

```text
[Ember 状态点 试运行 · 留白杂志海报] [主图 · 必需]

本次输入只用于验证方案，不会修改方案本身。
```

- 状态只在方案附件和一行低对比说明中表达，不改变整页颜色。
- 成功图片标记“试运行结果”并自动进入草稿相册。
- 失败结果不进入相册。
- 运行结束后保持试运行状态，提供“再试一次”“返回修改”“设为封面”“设为正式”。

### 8.3 修改方案

```text
[修改方案 · 留白杂志海报]

让标题区域更宽，并把默认比例改成 3:4。
```

- 用户输入默认修改方案本身，不自动显示运行变量。
- Agent 更新同一份草稿并返回简短修改摘要。
- 每轮自动保存，标题栏显示“草稿已保存”。
- 正式方案被修改时创建新草稿版本，原正式版本继续可用。
- Agent 不根据“试一下”等模糊文字静默切换模式，必须由用户点击“试运行”。

模式关系：

```text
修改方案 --试运行--> 试运行
    ^                    |
    +------返回修改------+

试运行 --设为正式--> 正式方案
正式方案 --使用--> 普通生图对话
```

## 9. 方案创建 Agent

### 9.1 创建原则

对话负责表达和修正，单一草稿区域承载当前结论，试运行证明方案可用。

1. Agent 读取文字、图片、历史或仓库。
2. 识别可复用的视觉规则和输入要求。
3. 可以合理推断时直接形成草稿。
4. 只有缺少真正阻塞运行的信息时才提问；一次只问一组相关问题并给出推荐默认值。
5. 每次修改更新同一份草稿，不生成重复方案卡片。

进度只描述真实动作，例如“正在读取仓库”“正在整理参考图片”“正在确认输入要求”“正在形成方案草稿”，不显示虚假百分比。

### 9.2 草稿区域

```text
方案草稿 · 草稿

留白杂志海报
将照片展开成克制的竖版纸张海报

需要提供
主图 · 必需
@标题 · 必需
@副文案 · 可选

来源
Skill · LiamGvchi/gc-minimal-zine-poster

[折叠相册 / 尚无结果]

[保存暂存]                           [试运行]
```

- 草稿保留在对话正文中，不使用常驻右侧结构化工作台。
- 页面标题栏显示“方案名称 · 草稿”，点击可以快速返回草稿位置。
- 关闭页面自动保存；在“我的方案 > 草稿”点击“继续”恢复。
- 一个创建过程只形成一个方案。来源包含多个明显不同的方法时，Agent 先列出候选方向，由用户选择一个。

## 10. 历史内容创建

### 10.1 来源选择

- 用户可以选择历史对话、具体消息和一张或多张图片。
- 从某张图片创建时，默认只关联图片、直接生成它的用户输入、提示词、参数、方案和参考图。
- 从对话创建时由用户勾选所需消息、图片和提示词；不自动读取整段对话。
- 附件显示类似“历史 · 2 张图片 + 1 条输入”，点击可以重新选择范围。

### 10.2 默认提取说明

历史来源进入 Composer 后，自动加入一段可见、可编辑的默认说明：

```text
从这些内容创建一个可复用方案。

保留视觉风格、构图方式、色彩与材质方向；
不保留具体人物、品牌名称和原始文案。
```

提供“保留人物特征”“保留文案结构”“保留品牌元素”“保留生成参数”“只参考其中一张图”等快捷建议。点击建议直接更新 Composer 中可见的说明，不在后台静默增加规则。

## 11. GitHub 地址识别

### 11.1 统一附件行为

- 单独粘贴仓库、Skill 子目录或 `SKILL.md` 地址：自动从正文转换为来源附件。
- 地址嵌入普通段落：保留正文，只提示“识别为方案”。
- Issue、Pull Request 和 Commit 地址不自动识别。
- 识别中显示 Ember 呼吸状态点；用户仍可编辑文字和添加图片，但不能发送。
- 删除附件会取消识别；撤销可以恢复普通文本链接。
- 识别失败保留原始链接，不自动删除。

### 11.2 识别结果

| 结果 | 动作 |
|---|---|
| 未添加的生图 Skill | 用户确认“添加为草稿” |
| 已有草稿 | 继续试运行 |
| 已有相同正式版本 | 使用 |
| 正式方案存在上游更新 | 创建草稿版本 |
| 普通提示词仓库 | 建议“从这个仓库创建方案” |
| 非生图 Skill | 不添加，显示具体原因 |
| 私有仓库未授权 | 保留来源，等待授权 |

GitHub Skill 不得静默安装。确认层显示方案名称、仓库、将读取的 Skill 文件、参考图片和提示词说明，并提供“取消”“查看详情”“添加为草稿”。

### 11.3 首次使用即试运行

用户在普通 Composer 粘贴未添加 Skill 后，可以保留当前文字和图片进入试运行。第一次成功生成被定义为本机试运行；完成后仍需用户选择封面并设为正式。

当前已有正式方案时再粘贴新 Skill，必须提示“继续后将保存当前输入，并进入新方案试运行”，确认后才切换。

创建方案模式可以把多个仓库作为来源，但最终只编译一个组合方案；普通生图模式仍只允许一个正式方案。

## 12. 动效、可访问性与验收

### 12.1 动效

- 页面切换约 `160ms`，使用轻微透明度和位移；不使用弹跳、翻牌或装饰运动。
- GitHub 识别状态可以缓慢呼吸，但必须支持 `prefers-reduced-motion`。
- 相册切换约 `200ms`，只使用 transform 和 opacity。
- 动态内容通过 `aria-live` 表达；不能只依赖颜色说明状态。

### 12.2 可访问性

- 键盘可完成方案搜索、选择、替换、移除、变量填写、相册切换和转为正式。
- 所有图标按钮有可见 tooltip 和辅助技术名称。
- 交互目标至少 `44 x 44px`，可见焦点满足 WCAG 2.2 AA。
- 长方案名、长仓库名、窄窗口和 200% 缩放不能造成文字遮挡或按钮位移。
- 图片预览必须提供来源、序号和可用的替代文本。

### 12.3 第一版验收

- 方案中心只有“我的方案/发现”，没有独立 Skills 顶级页面。
- 草稿不会出现在普通 Composer 方案选择器中。
- 添加 Skill 后必须本机试运行并由用户确认，才能转为正式和普通调用。
- 方案中心、详情、Composer 对草稿/正式状态显示一致。
- 折叠相册能区分查看对象与永久封面，且完整显示不同长宽比图片。
- Composer 同时支持具名图片槽位、结构化 `@变量` 和自由输入。
- 使用、试运行、修改三个模式不会互相静默改变数据。
- 历史来源范围和提取说明始终由用户看见并可修改。
- GitHub 识别、确认、失败、更新和取消不会丢失 Composer 内容。
- 创建过程持续更新同一份方案草稿，不回退为三栏结构化工作台。
