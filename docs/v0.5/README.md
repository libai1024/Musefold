# v0.5 · 账号与云通道（Musefold Account & Cloud Relay）

> **状态**：实现中（2026-08-13：账号内核、托管双栈、双轨 Onboarding、兑换/定价/公告、错误闭环与成本看板已落地并通过单测/E2E；发布冻结待完成）
> **日期**：2026-08-13
> **前置**：v0.3.3 已实现基线（双凭据体系：生图 Provider + 文本 AI 连接）；v0.4 Agent Surface 并行开发中（关系见 §7）
> **本目录是 v0.5 的事实来源**：实现应以本目录文档为准；与旧文档冲突时，遵循 `docs/README.md` 的权威顺序（源码 > 版本文档 > 决策 > 历史交接）。

## 1. 一句话目标

**让用户注册 / 登录一个 Musefold 账号后，文本 AI 与生图能力全部自动配置完成（一次登录 · 畅享所有模型 · 全程不接触 API Key）；同时完整保留"自备 API / 自建中转站"的高级路径。**

v0.5 之后，新用户的首次体验从「找两个服务商 → 充值 → 复制两个 Key → 分别粘贴到两个设置界面」收敛为「注册 → 输入兑换码 → 出第一张图」；运营者（项目所有者）通过自托管的 new-api 中转站集中管理上游、模型、额度与用户。

---

## 2. 背景与动机

1. **两次 Key 是当前最大的上手摩擦**。App 存在两套独立凭据体系——生图 Provider（SQLite `providers` 表 + OS keychain）与文本 AI 连接（electron-store + `ElectronAiSecretKeychain`）。即使两边用同一家中转站，用户也要在两个界面各配置一次；用悟空生图 + 其他文本服务商时更要管理两个账号、两笔余额。
2. **BYOK 模式把获客门槛外包给了第三方**。用户必须自行注册第三方中转站、充值、理解 baseUrl / 模型 ID 等概念，流失点全部在 App 掌控之外。
3. **自托管中转站让上游可替换**。运营者当前的上游本质是第三方中转站（TvT 等）；套一层自己的 new-api 后，上游渠道随时可增删切换，用户无感知。
4. **发码制冷启动**。零初始额度 + 兑换码激活，让内测阶段的用户规模与成本完全可控，且抵消纯用户名注册的批量滥用风险。
5. **v0.3 的安全红线在 v0.5 依然成立**：密钥/凭据只在主进程、`safeStorage` 加密落盘、日志与导出永不含密钥。账号体系是在这条红线之上叠加，不是替代。

## 3. 范围

### 3.1 In Scope（v0.5 交付）

| 编号 | 交付物 | 说明 |
|---|---|---|
| S1 | Musefold Cloud 中转站（服务端） | 阿里云 ECS 自托管 new-api：Docker Compose 部署、渠道/别名/额度/兑换码配置基线、运营 SOP |
| S2 | 账号内核（`electron/account/`） | new-api 用户 API 客户端、登录编排、设备令牌供给、凭据入 keychain、IPC `account:*` |
| S3 | 托管双栈供给 | 登录后自动创建并激活两条 `managedBy: 'account'` 记录（生图 Provider + 文本连接），登出回收 |
| S4 | 设置页「账号」面板 | 未登录 / 已登录 / 额度为零 / 凭据失效四态；兑换码直充；服务器地址高级配置 |
| S5 | Onboarding 双轨改造 | 「登录账号（推荐）」与「使用自己的 API（高级）」两轨；账号轨含零额度兑换步 |
| S6 | 错误闭环 | 401 → 重新登录；额度不足 → 兑换码弹窗；网络/服务器错误统一文案 |
| S7 | 高级轨增强 | 网关类 preset 提供「一份 Key 同时用于文本与生图」，BYOK 用户也告别两次输入 |

### 3.2 Out of Scope（明确不做）

- ❌ 自研账号后端 / BFF（直连 new-api 用户 API；接口抽象层预留替换位）
- ❌ 在线支付（易支付 / Stripe 留作 v0.5.x 或 v0.6 评估；v0.5 只做兑换码）
- ❌ 自助找回密码、邮箱/手机号绑定、2FA 账号在 App 内登录（2FA 用户引导走网页）
- ❌ 悟空生图（`wukong-studio` 协议）进云通道——非 OpenAI 兼容协议，保留高级轨直连
- ❌ 多账号并存与切换（单账号；换号 = 登出再登录）
- ❌ 账号凭据、登录/兑换请求暴露给 v0.4 控制面 / CLI / MCP（红线，见 D12；允许脱敏就绪状态与原生界面唤起）
- ❌ 状态栏余额常显、用量图表（Phase 2 候选，见交付计划 §5）

## 5. 核心决策（D1–D12）

> 标注「✅ 已拍板」的为 2026-08-13 与产品所有者确认的决策；「✅ 建议锁定」为技术上基本无争议项。

| # | 决策 | 结论 | 理由摘要 |
|---|---|---|---|
| D1 | 服务端选型 | ✅ 自托管 [new-api](https://github.com/QuantumNous/new-api)（AGPL-3.0，2026-08 约 45k star，v1.0.0 已发布），不自研 | 账号/令牌/额度/兑换码/渠道全部开箱即用；社区头部、更新活跃；App 已有 `new-api` 网关 preset |
| D2 | 上游策略 | ✅ 服务器渠道对接现有第三方中转站（TvT 等）；上游 Key 只存在服务器 | 上游可替换、用户无感知；App 端零上游耦合 |
| D3 | 集成方式 | ✅ App 主进程直连 new-api 用户 API，不建 BFF；`account/api-client` 做接口抽象 | 少一个自维护服务；new-api 用户模块有公开文档；抽象层保留未来替换空间 |
| D4 | 注册方式 | ✅ 已拍板：**纯用户名 + 密码**（服务器关闭邮箱验证与 Turnstile） | 表单最简；无法自助找回密码 → 管理员重置 SOP（V05-SERVER-SPEC §5）；滥用风险由 D5 化解 |
| D5 | 额度策略 | ✅ 已拍板：**新用户初始额度 0，兑换码激活** | 批量注册的空账号无价值；用户规模与成本完全由发码控制 |
| D6 | 默认模型 | ✅ 已拍板：**服务器别名决定**——渠道配置 `musefold-agent` / `musefold-image-pro` 两个重定向别名；App 托管记录默认使用别名，别名缺失时兜底（`gpt-5.4-mini` / `gpt-image-2`） | 换默认模型不发版、全员即时生效；兜底保证自建 new-api 的用户可用 |
| D7 | 凭据模型 | ✅ 密码仅内存态、永不落盘；access_token（管理面）与设备令牌 sk-（调用面）经 `safeStorage` 入 OS keychain | 延续 v0.3 红线；两类凭据分离——调用凭据长期有效，管理凭据失效只影响账号面板 |
| D8 | 托管供给 | ✅ 登录成功后自动创建两条 `managedBy: 'account'` 记录（生图 Provider + 文本连接，同一 sk- 令牌、同一 baseUrl）并设为激活；登出全部回收 | 复用现有双栈请求路径与激活机制，生图/文本调用代码**零改动**；"一次登录配好一切"的直接实现 |
| D9 | 令牌粒度 | ✅ 每设备一枚令牌（命名 `musefold-<平台>-<短id>`），id 存本机账号 store | 网页端可单独吊销某台设备；换机不互踢 |
| D10 | 双轨共存 | ✅ 账号轨与自备轨共用现有「激活」语义，互不排斥；高级轨保留悟空直连；网关 preset 增加「一份 Key 配两栈」 | 不引入新概念；老用户配置零迁移；BYOK 痛点顺带解决 |
| D11 | 服务器地址可配置 | ✅ 默认内置官方站地址（`shared/constants` 常量），账号面板高级项可改 | 任何自建 new-api 的用户/团队也能用登录模式，自备中转站体验同级 |
| D12 | 自动化面隔离 | ✅ 账号凭据与 `account:*` 登录/兑换操作**不**暴露给 v0.4 控制面 / CLI / MCP；自动化只可读取脱敏就绪状态、选择已配置 Provider、唤起原生配置页，所有凭据仍由用户在 App 内输入 | Agent 上下文不可信（V04-SECURITY 红线延续）；兼顾零凭据暴露与低配置门槛 |

## 6. 目标体验（North Star 场景）

### 场景 A：新用户 3 分钟出第一张图

```text
下载安装 → 打开 App → 引导页选「登录账号（推荐）」
  → 注册（用户名 + 密码，即注册即登录）
  → 检测到额度为 0 → 就地输入兑换码 → 余额到账
  → 自动校验（文本 ✓ 生图 ✓）→ 示例提示词出第一张图
全程 0 次 API Key 接触、0 次跳出 App。
```

### 场景 B：额度耗尽的闭环

```text
创作台生成失败（额度不足）→ 错误卡直接给「输入兑换码」按钮
  → 兑换成功 → 「重试」原地续跑。
用户不需要理解"配额/倍率/渠道"，只需要一张码。
```

### 场景 C：高级用户自备中转站

```text
设置 → AI 服务 → 新建连接（自己的 new-api / LiteLLM / 任意 OpenAI 兼容站）
  → 勾选「同时用于文本与生图」→ 粘贴一次 Key → 双栈配置完成。
账号托管记录仍在列表中，随时可切回。
```

### 场景 D：自建 new-api 的团队

```text
账号面板 → 高级 → 服务器地址改为 https://ai.example.com
  → 用团队账号登录 → 托管供给照常工作。
Musefold 官方站与自建站在 App 里是同一种东西。
```

## 7. 与 v0.4（Agent Surface）的关系

| 关注点 | 结论 |
|---|---|
| 开发时序 | 可并行。账号内核（S2/S3）不依赖 v0.4 交付物；唯一共享的改动面是主库 `providers` 表迁移（已随 V04-CORE-03 移入 `packages/core/src/db/migrations/`，v0.5 在同一机制下追加迁移文件） |
| 生图路径 | 托管 Provider 是一条普通的 `openai-compatible` 记录，v0.4 GenerationService（V04-CORE-05）无需感知账号存在 |
| 控制面 / CLI / MCP | 按 D12 隔离：不暴露登录、注册、兑换或任何凭据；仅提供脱敏状态、已配置 Provider 切换与原生设置页唤起，`provider list` 中托管条目保持只读 |
| 密钥红线 | 与 V04-SECURITY 完全一致：明文凭据永不出主进程；MCP/CLI 无凭据读取面 |

## 9. 术语表

| 术语 | 含义 |
|---|---|
| **中转站 / 云通道** | 自托管的 new-api 实例，向 App 暴露 OpenAI 兼容 `/v1` 接口，向上游中转站转发请求 |
| **账号服务器** | 同上（中转站同时承担账号/令牌/额度职责）；App 内默认指向官方站，可配置 |
| **托管记录** | 登录后由账号服务自动创建的生图 Provider / 文本连接条目，`managedBy: 'account'`，只读、登出回收 |
| **设备令牌** | 每台设备一枚的 new-api API 令牌（`sk-` 前缀），是 `/v1` 调用凭据，长期有效 |
| **access_token** | new-api 用户级管理凭据，用于查余额、建令牌、兑换等 `/api/*` 管理请求；失效只影响账号面板 |
| **兑换码** | new-api 充值码（管理后台生成，线下发放），`POST /api/user/topup` 核销 |
| **别名模型** | 服务器渠道模型重定向出的 `musefold-agent` / `musefold-image-pro`，用于服务端控制默认模型 |
| **账号轨 / 高级轨** | Onboarding 与设置中的两条配置路径：登录托管 vs 自备 API（BYOK） |
| **双栈** | App 既有的两套凭据体系：生图 Provider（SQLite + keychain）与文本 AI 连接（electron-store + keychain） |
