## 1. 问题陈述

### 1.1 现状

App 存在两套彼此独立的凭据体系，用户为了用全 AI 能力必须配置两次：

| | 生图 Provider | 文本 AI 连接 |
|---|---|---|
| 存储 | 主库 SQLite `providers` 表 | electron-store（`musefold-ai-connections-*`） |
| 密钥 | `electron/security/keychain.ts`（safeStorage） | `electron/security/ai-keychain.ts`（safeStorage） |
| 配置入口 | Onboarding 步骤 2 · 设置 → 服务商 | 设置 → AI 连接 |
| 预设 | TvT（`gpt-image-2`）、悟空生图组 | TvT（`gpt-5.4-mini`）、DeepSeek、Kimi、GLM、MiniMax、LiteLLM、New API、自定义 |
| IPC 面 | `provider:*` | `aiConnection:*` |

### 1.2 痛点

1. **配置成本**：新用户需理解"服务商 / baseUrl / 模型 ID / API Key"四个概念、跳出 App 到第三方站注册充值、在两个设置界面各粘贴一次 Key。
2. **凭据心智负担**：两个 Key、两笔余额、两处失效来源；README FAQ 中 `AUTH/401` 常见问题即来源于此。
3. **运营不可控**：获客转化的关键路径（注册、充值）完全发生在第三方中转站，App 无法优化。
4. **上游锁定**：预设直接指向具体第三方站；上游更换需要发版并让全体用户重新配置。

### 1.3 机会

自托管 new-api 中转站（D1/D2）把上游收敛到服务器一侧后，App 端只需对接**一个**账号体系，即可同时供给文本与生图两栈；发码制（D5）使冷启动成本可控。

## 2. 目标与成功指标

### 2.1 目标

| # | 目标 | 度量 |
|---|---|---|
| G1 | 新用户从安装到出第一张图 ≤ 3 分钟（账号轨，含注册与兑换） | P3 真机秒表验收（3 台设备 × 冷装） |
| G2 | 账号轨全程 **0 次** API Key 接触 | 产品走查：任何界面不出现 Key 输入/展示（除高级轨） |
| G3 | 高级轨（BYOK）能力不退化，且网关类配置从 2 次 Key 输入降为 1 次 | E2E：既有 BYOK 用例一条不删全绿 + 新增"一份 Key 配两栈"用例 |
| G4 | 上游切换不发版：服务器改渠道/别名后，存量客户端无感知继续工作 | P3 演练：切换别名指向，验证 App 无需任何操作 |
| G5 | 密钥/凭据安全边界与 v0.3 等强 | NFR-SEC 全项通过（含日志/导出脱敏审查） |

### 2.2 反目标（刻意不追求）

- 不追求账号转化漏斗遥测——App 保持本地优先、零遥测；运营数据从服务器侧（注册数、活跃令牌、消耗日志）获取。
- 不追求首发即支持在线支付；兑换码是 v0.5 唯一充值方式。

## 4. 用户故事与验收标准

> 验收采用 Given / When / Then；每条故事标注涉及的 FR。

**US-01 注册即登录**（FR-ACC-01/02，FR-GW-01/02）
作为新用户，我在 App 内用用户名和密码注册后，无需再次登录即进入已登录状态，文本与生图配置自动就绪。
- Given 引导页账号轨注册表单，When 提交合法用户名+密码且服务器返回成功，Then App 处于已登录态，服务商列表与 AI 连接列表各出现一条「Musefold 账号」托管记录并均为激活态。

**US-02 零额度引导**（FR-ACC-05/06，FR-OB-03）
作为新注册用户，我登录后额度为 0 时，App 直接让我输入兑换码，而不是让我带着一个不能用的账号进入主界面。
- Given 登录成功且 `quota = 0`，When 进入 Onboarding 下一步，Then 显示兑换码输入步骤；When 兑换成功，Then 显示到账额度并自动进入校验步骤。

**US-03 一次登录畅享所有模型**（FR-GW-06/07）
作为已登录用户，我在文本模型与生图模型选择器里能看到服务器分组放开的全部模型，不需要任何额外配置。
- Given 已登录，When 打开模型选择器并刷新，Then 列表与服务器 `/v1/models`（按令牌分组过滤）一致；默认模型为服务器别名（缺失时为 App 兜底值）。

**US-04 额度耗尽闭环**（FR-ERR-02）
作为创作中的用户，生成因额度不足失败时，我能在错误提示里直接输入兑换码并原地重试。
- Given 生成请求返回额度不足错误，Then 错误卡包含「输入兑换码」动作；When 兑换成功并点击重试，Then 原参数重新提交。

**US-05 凭据失效闭环**（FR-ACC-10，FR-ERR-01）
作为用户，当我的设备令牌被吊销或删除后，App 明确告诉我"重新登录即可修复"，且重新登录后一切恢复。
- Given 托管记录调用返回 401，Then 全局提示「账号令牌失效，请重新登录」；When 重新登录，Then 重新供给设备令牌，原功能恢复，无孤儿记录残留。

**US-06 登出即回收**（FR-ACC-03，FR-GW-04）
作为用户，登出后我的凭据与托管配置从本机彻底消失，但我手动创建的配置原样保留。
- Given 已登录且另有手动配置，When 登出，Then 托管记录、keychain 中的设备令牌与 access_token 全部删除；激活权回落到最近更新的手动记录；无任何账号凭据残留于磁盘。

**US-07 BYOK 不受影响**（FR-GW-05，FR-OB-05）
作为存量 BYOK 用户，升级到 v0.5 后我的服务商、连接、Key、激活状态与 v0.3.x 完全一致。
- Given v0.3.x 数据目录，When 首次以 v0.5 启动，Then 迁移后 `providers` 全部记录 `managed_by = NULL`、行为不变；不弹 Onboarding（`onboarded` 已置位）。

**US-08 一份 Key 配两栈**（FR-OB-06）
作为自备中转站的用户，我在高级轨选网关类预设时，勾选「同时用于文本与生图」后只粘贴一次 Key。
- Given 高级轨选择 TvT / New API / LiteLLM / 自定义网关预设并勾选该项，When 保存，Then 两栈各生成一条记录、各自 keychain 写入同一 Key，且都通过各自校验。

**US-09 自建站登录**（FR-ACC-08）
作为自建 new-api 的团队成员，我把账号服务器地址改成团队站后，登录托管流程与官方站完全一致。
- Given 账号面板高级项填入合法 https 地址，When 登录成功，Then 托管记录 baseUrl 指向该站；别名模型缺失时使用兜底默认值且校验仍通过。

**US-10 运营者切换上游**（FR-SRV-03；G4）
作为运营者，我在 new-api 后台把别名指向新模型/新渠道后，所有客户端下一次请求即生效。
- Given 存量客户端正常使用，When 服务器修改 `musefold-*` 别名映射或渠道，Then 客户端无需更新、无需重登录，请求继续成功。

**US-11 成本可信**（FR-COST-01/02/03）
作为账号用户，成本看板里的消费数字与服务器实际扣费一致，我还能直接看到余额大约够生成多少张。
- Given 已登录并完成若干次生成，When 打开成本看板，Then 托管消费以「点」显示、金额与服务器扣账一致；汇总区显示余额与「约可生成 N 张」；旧 BYOK 记录仍以 ¥ 正确显示。

## 5. 功能需求（FR）

### 5.1 账号内核（FR-ACC）

| 编号 | 需求 | 优先级 | 备注 |
|---|---|---|---|
| FR-ACC-01 | 注册：用户名+密码提交 `POST /api/user/register`；成功后自动执行登录编排 | P0 | 用户名/密码前端校验规则与服务器约束一致（P1 联调冻结，保守基线：用户名 3–30 字符，密码 ≥ 8） |
| FR-ACC-02 | 登录编排：`POST /api/user/login` → 获取 JWT（内存）+ refresh 凭据（keychain）→ 幂等供给设备令牌（`POST /api/token/{id}/key` 取回明文）→ 托管双栈写入 → 刷新余额 | P0 | 全流程原子性：任一步失败则回滚已写入的托管记录，账号态为未登录并给出可读错误 |
| FR-ACC-03 | 登出：删除本机 access_token、设备令牌 keychain 条目与两条托管记录；不调服务器吊销（网页端可自行吊销） | P0 | 服务器不可达也能完成本地登出 |
| FR-ACC-04 | 账号状态持久化与查询：`account:status` 返回 `{ loggedIn, username, serverUrl, quota?, tokenSuffix?, health }`；启动时从本地缓存恢复，不阻塞启动做网络请求 | P0 | `health: 'ok' | 'token-invalid' | 'unreachable' | 'unknown'` |
| FR-ACC-05 | 兑换码充值：`account:redeem` 调 `POST /api/user/topup`，成功后立即刷新余额 | P0 | 失败区分：码无效/已用/网络错误 |
| FR-ACC-06 | 余额查询：`account:refreshQuota` 调 `GET /api/user/self`；面板打开、兑换成功、登录成功后各触发一次 | P0 | 展示换算规则见 OQ-03（P1 冻结） |
| FR-ACC-07 | 设备令牌供给幂等：本机记录令牌 id；已存在且有效则复用，缺失/失效则新建（命名 `musefold-<platform>-<4位随机>`），并同步覆写两栈 keychain | P0 | 令牌明文取回能力依赖 OQ-01；不可取回时降级为"每次登录新建并覆写" |
| FR-ACC-08 | 服务器地址可配置：默认 `DEFAULT_ACCOUNT_SERVER_URL` 常量；账号面板高级项可改（复用 `normalizeAiBaseUrl` 校验，仅允许 http/https、无凭据、无 query）；改地址强制先登出 | P1 | D11 |
| FR-ACC-09 | 凭据安全存储：密码仅存在于内存中的请求作用域；JWT 仅驻留主进程内存（不落盘）；refresh 凭据与设备令牌经 safeStorage 写 OS keychain；任何日志/诊断/导出不含凭据 | P0 | NFR-SEC 联动 |
| FR-ACC-10 | 管理凭据静默续期与失效处理：JWT 过期（约 30 分钟）经 `POST /api/user/auth/refresh` 静默续期（refresh 凭据约 30 天、每次轮换）；refresh 失效才置 `token-invalid` 并引导「重新登录」；**不**自动清除设备令牌（调用面可能仍有效） | P0 | 三层自愈矩阵见架构文档 §5.4；调用面 401 处理见 FR-ERR-01 |

### 5.5 成本看板（FR-COST，账号模式适配）

> 既有成本看板（`CostDashboard.tsx`，本地账本聚合、人民币分计价、"非真实账单"免责）在账号模式下三个前提被打破：单价不再是用户手填估算而是服务器真实计费；计价货币从人民币变为点（美元锚定）；用户多了"余额"这一核心心智。以下需求让看板在两种模式下都诚实。

| 编号 | 需求 | 优先级 | 备注 |
|---|---|---|---|
| FR-COST-01 | 余额卡：已登录时看板汇总区首位显示「账号余额」卡——余额点数 + 「约可生成 N 张」（N = quota ÷ 当前生图单价点数，主进程按 FR-GW-09 定价计算，随 `AccountStatus` 下发）；未登录不显示此卡 | P1 | 打开看板时触发一次余额刷新（与 FR-ACC-06 合并节流） |
| FR-COST-02 | 成本真值化标注：托管 Provider 的消费在明细与免责声明中标注「按账号实际计费单价统计」；「配置单价」动作对托管 Provider 跳转账号面板（单价只读、随服务器同步），对 BYOK 保持现状；托管 Provider 不触发"未配置单价"警告 | P1 | FR-GW-09 的看板呈现面 |
| FR-COST-03 | 记账单位快照：`history` 表新增 `cost_unit` 列（`'cny_cent'` 缺省 \| `'point'`），生成入账时按 Provider 来源快照；托管记录以「点」记账（per-image = `model_price × 500000`，与服务器扣费一致）；统计聚合按单位分组，「累计花费」卡在混合时双行显示（「N 点」/「¥X」）；`formatCost` 支持点单位 | P1 | 旧数据零迁移损失（默认 cny_cent）；登出后历史记录单位解释不依赖 Provider 存活 |

### 5.6 错误闭环（FR-ERR）

| NFR-REL-01 | 可靠性 | 账号服务器不可达时：高级轨与已缓存的托管调用路径不受管理面故障影响；所有账号操作有超时（10s）与可读错误 |

## 8. 明确不做（产品拍板，2026-08-13）

> 以下功能经产品所有者确认**不做，以后也不做**。服务端接口虽存在（rc.24 路由已盘点），但 App 永不接入；再次提出需重新立项评审。

### 8.1 永久排除（2026-08-13 拍板）

- **邀请体系**（`aff_code` 注册、邀请码面板、奖励划转）。
- **用量明细页**（`GET /api/log/self` 服务器日志复刻）——成本透明度由本地成本看板承担（FR-COST）。
- **逐 token 成本预估**（生成前预估卡）。
- **在线充值**（waffo / 易支付 / Stripe）——兑换码是唯一充值方式。
- **订阅套餐**。
- **分组/会员档位**（`group` 字段仅作为只读信息保留在 getSelf 解析中，不做任何产品化）。
- **2FA / Passkey 的 App 内登录**——此类账号引导网页控制台。

### 8.2 职责在服务器或网页控制台（App 不做）

- 渠道故障转移/自动重试/负载均衡——new-api 服务端职责，App 无感。
- 改密码、删号、令牌批量管理——网页控制台已有，避免双实现。
- 自助找回密码（依赖邮箱/手机绑定）、多账号切换。
- 悟空生图协议适配层（使其可进云通道）。
- 账号能力进入 v0.4 自动化面（若未来放开，须重走安全评审）。
