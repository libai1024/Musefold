## 2. 实施前的实际缺口（保留诊断依据）

上游已有50条活跃会话上限、24小时100次签发限制、30天会话绝对期限，以及每小时清理过期会话/保留7天撤销记录的维护任务。运行环境没有覆盖这些会话参数。`last_active_at` 主要在refresh时更新，不能直接解释为前台用户最近操作时间。

已存在且可复用的上游接口：

- `GET /api/user/sessions`：已认证会话的脱敏列表。
- `DELETE /api/user/sessions/:sid`：仅撤销当前账号下指定会话。
- `POST /api/user/sessions/revoke-others`：已登录用户撤销其他会话。
- `POST /api/user/auth/logout`：按access/refresh和 `X-Auth-Session` 核对本次会话后退出。

缺口不是只有“上限太小”：

1. Musefold `NewApiClient` 尚无logout/会话管理方法。Web和Desktop均调用Musefold `/api/auth/sign-out`，删除Better Auth会话；`relay_sessions`随FK级联删除，但上游登录仍可占位。桌面还先清本机凭据，再尽力远端退出，离线时没有持久补偿。
2. 上游登录成功、Musefold身份核对/建会话失败时，缺少完整上游撤销补偿。重复测试和失败重登都可能积累孤儿会话。
3. 上游满额返回 `AUTH_SESSION_LIMIT`，不发普通登录凭据。现有列表接口要求已登录，不能解决“所有设备都不可访问”的满额用户。
4. 上游当前计数与创建不是同一个用户行锁事务；新方案必须一起补并发准入，不能在客户端先删后登。
5. Better Auth内置 `/list-sessions` 返回其他设备原始token，当前禁止是正确的，**继续禁止**，不拿它作为新UI数据源。

源码依据：Musefold `packages/new-api-client/src/index.ts`、`apps/api/src/auth/{index,new-api-delegation}.ts`、`packages/db/src/schema/credentials.ts`、Desktop `ipc-v25/account-domain.ts`；上游精确提交的 `service/auth_session.go`、`service/auth_token.go`、`service/auth_cleanup.go`、`model/user_session.go`、`controller/{user,auth_session}.go`、`router/api-router.go` 和 `common/{constants,init,redis}.go`。

## 3. 自动释放策略（实现默认）

| 情况 | 处理 | 不做的事 |
|---|---|---|
| 用户明确退出 | 本地授权立即失效，同步撤销对应上游SID；失败进入持久补偿 | 不撤销其他设备，不把断网当退出已完成 |
| 登录中途失败/候选被新意图替代 | 清理本次候选会话；创建前登记操作、失败后可恢复补偿 | 不撤销原来仍有效的账号或设备 |
| 已过绝对期限 | 鉴权、登录准入立即排除，后台分批清理 | 不等定时任务运行才腾名额 |
| 新机制建立的会话连续7天无真实使用 | 自动失效并释放；30天绝对上限不延长 | 不凭窗口关闭、断网或几分钟静默踢人 |
| 当前仍活跃/正在交互 | 保留；满额由用户显式选要退出的设备 | 不默认LRU踢最老的活跃设备 |
| 已登录设备刷新/恢复 | 使用当前有效会话刷新，不另签一条 | 不按相同IP/UA合并设备或授予权限 |
| 自动测试结束 | finally按创建时记录的精确SID退出；崩溃由受限生命周期回收 | 不让每轮测试都再强制清空账号 |

保留现有50条活跃上限与100次/24h防滥用限制，不用调大阈值或关闭限制掩盖泄漏。100次签发限制与活跃名额分开：退出不能重置签发次数；返回独立错误和可核对的最早重试时间。

闲置规则依赖新 `last_interactive_at`，由已认证业务活动有界更新（最多每5分钟写一次），后台轮询/静默refresh只更新存活信息，不能无限续闲置期限。30天绝对期限从创建起算。旧会话没有可信交互时间时标为未知，仅沿原绝对期限或用户手动退出，不把历史refresh时间当新闲置证据。策略版本随新会话保存；不追溯性踢掉存量活跃设备。维护每5分钟分批执行，并在新登录准入事务中重算过期/闲置资格。

“释放登录”不删除作品、提示词、同步队列、历史、费用或API生图凭据，也不隐式取消/重新发起生成。尚未获得发送资格的任务遵守既有会话失效准入；已发送任务保留原回执和费用结算，重新登录后按原任务核对，不承诺退出能撤回已发生调用。

## 4. 新登录满额流程

```text
输入凭据 → 上游密码校验 / 必要的2FA或其他既有验证
    ├─ 不通过：保持原认证错误；不透露会话/账号存在性
    └─ 通过 → 按账号加锁，回收已失效会话并核对容量/签发频率
         ├─ 有名额：创建登录，Musefold完成可信身份核对
         ├─ 签发频率超限：等待明确重试时间，不允许撤销绕过
         └─ 活跃名额已满：签发5分钟“仅管理本次登录容量”挑战
              → 显示已登录设备，默认全部不选
              → 用户选择 → 确认“释放所选并登录”
              → 原子撤销固定所选SID + 占用释放名额 + 创建新登录
```

必要的上游协议增量，而非在Musefold绕过登录：

- 挑战只在完整认证后创建，绑定权威userId/issuer、auth_version、登录方式、请求方随机绑定和期限；仅允许列出该账号会话及完成一次固定选择的登录。不得访问模型、额度、业务数据、MCP或发起收费请求。
- 沿现有上游 `auth_flows` 加专用purpose；挑战secret只存摘要；Musefold委托层加密暂存，不传给renderer、不放URL/localStorage/日志。Web由HttpOnly/Secure/SameSite的临时请求方cookie绑定，Desktop由主进程持有绑定秘密，renderer仅拿无独立权限的flowRef。
- 旧版上游未声明新协议能力时，明确显示尚不支持满额自助恢复及可用的官方入口；绝不伪造设备列表或把一般409视为密码验证凭证。
- 已落地协议v1：New API `POST /api/user/managed-login/{begin,review,complete,cancel,release}`，已登录管理为`/api/user/managed-sessions`及其`touch/revoke`子路由；私有响应schema在`contracts/relay-login-sessions.ts`。请求中的owner/issuer不能覆盖挑战内绑定值。
- complete在一个上游用户行锁事务内重验账号状态、auth_version、挑战、签发次数、所选SID所属账号和安全版本；所有登录入口使用同一锁/计数纪律。只允许用户看到并选中的会话，最多50条，去重且拒绝未知/越权ID。
- 若期间已有设备退出，按真实容量重新计算；名额已够则不再无谓踢出其他设备。若仍不足或所选依据失效，返回需要重新核对的列表，不自动换选另一台设备。
- 多端同时抢最后一个名额时，仅一方提交；另一方不额外撤销设备，回到核对。事务失败不留下部分数据库撤销或超额新会话。
- Redis拒绝屏障与持久撤销保持现有安全语义；成功响应前确认已阻止旧会话，测试延迟cache fill/Redis失败/进程崩溃，不能只修改PG后宣称即时安全退出。
- 同一次complete带幂等operationId与固定选择摘要；重复提交返回同一个结果，不再签发。丢回包可通过同一请求方绑定短期恢复加密保存的原登录交付；不得缓存明文密码，也不能重新运行收费操作。过期只清临时状态，不能顺手退出任何旧会话。
- 新上游会话已建但Musefold身份核对失败，补偿撤销新候选。用户已明确释放的旧设备不会被偷偷复活，界面说明需重新登录；跨两个数据库不宣称分布式原子性。

## 5. 已登录会话管理

落点与状态矩阵以 [UI规范§7.1A](./V25-UI-SPEC.md) 为单一基准。列表来自上游安全投影与本服务可信会话映射，严格按issuer+owner隔离。显示设备/客户端、当前设备、登录时间、最近使用、失效时间及掩码IP；UA只作有长度限制的展示线索，无法判断时显示未知，不当设备身份证据。

完整SID、JWT、refresh、refresh摘要、Better Auth token、内部principal映射和任意原始upstream对象不进入公开合同。UI使用非授权性的sessionRef；服务端映射精确上游SID。SID本身不是密码，但也不需要在页面暴露。

已实现的共享契约（`contracts/login-sessions.ts`，zod与z.infer）：

- `LoginSessionView`：sessionRef、version、client、platform、current、createdAt、lastInteractiveAt/lastSeenAt（nullable）、expiresAt、maskedIp。sessionRef加密并绑定当前flow或BA会话，不能跨scope挪用。
- `LoginSessionsPage`：items、total、limit、required、requiresReauthentication。当前上限50，返回完整列表，schema强制total等于items数量，截断不冒充完整列表。
- `RevokeLoginSessions`：operationId、selected中的sessionRef+version、需要时password/twoFactorCode；返回实际released数量，0不冒称踢下一台。未知结果保留原operationId与固定选择，二次验证可在确认窗内重新输入；不保留已提交密码。
- `LoginCapacityReview`：flowRef、expiresAt、所需名额及安全投影列表；`completeLogin`返回普通成功结果或新一轮核对需求。它和B12“历史身份恢复”是不同状态、不同scope，不共用恢复权限。
- Gateway：`account.listLoginSessions/revokeLoginSessions/getLoginCapacityReview/completeLoginCapacity/cancelLoginCapacity/touchLoginSession`；Desktop另有仅返回pending数量的`getLoginReleaseStatus`。认证端点统一委托New API，挑战过程中不创建正常业务会话。

当前设备退出复用原登出语义；释放其他设备需要有效正常身份和CSRF/来源检查。敏感批量退出要求近期重新验证；受限历史身份不能管理另一个已验证主体的设备。服务返回 `Cache-Control: private, no-store`，错误不带原始响应。

## 6. 持久释放、掉线与竞争

本服务会话失效与上游撤销是两个阶段。使用服务端加密释放队列，唯一键为issuer+上游SID，带reason、attempts、nextAttemptAt、lease、confirmedAt、上游期限；队列不随Better Auth FK级联消失。删除本地会话前，在同一个PG事务捕获释放责任；覆盖显式退出、到期维护、候选失败、账号关闭及BA内部删除，不只在单个HTTP handler写finally。

刷新与删除统一锁序并校验revision；刷新晚到不能重建已删除会话。网络不在PG锁内执行。上游撤销worker按固定issuer发送、不跟随重定向，逐项确认后才销毁释放用密文；进程崩溃/超时重放原撤销操作。指数退避（5秒、30秒、2分钟，之后至多15分钟）及积压告警；达到原上游绝对期限并得到权威过期依据后可结束，不无限保留凭据。

当前上游的轮换refresh有一个重要限制：过了重放宽限，旧refresh失效不等于整条session已撤销。因此不能把任意401当释放成功，也不能盲目刷新旧token造成额外副作用。完整协议需支持**单SID、仅撤销权限的稳定清理凭据**：随新会话签发、上游只存摘要，绑定owner/SID/绝对期限；仅由Musefold服务端加密保管，可重复撤销本SID，不能读资料、换JWT或撤销其他设备。不把该凭据发送到浏览器或桌面渲染层。旧会话没有此能力时，只使用可信当前授权调用既有撤销接口；无法确认则保留“远端待确认”，最终由期限回收，不能声称即时释放完成。

Desktop离线退出立即清可用登录、停旧账号访问；先将原服务的退出责任写入safeStorage密封小队列，再清当前会话，不丢失远端释放责任。下次联网只向原issuer重试，不用新账号凭据代办；也不持有可用的UI登录状态。UI明确“本机已退出，远端释放待联网确认”。正常关闭App/浏览器标签不自动退出，避免破坏持久登录与同步恢复。

登录创建也须有operationId与短期候选租约：上游成功回包丢失或API在持久化候选前崩溃时，可恢复同一个候选或到期释放，不再创建无法追踪的新会话。正式激活与取消需竞争仲裁；已经激活的会话不会被迟到候选清理撤销。

## 7. 实施与验证顺序

1. 先止住新泄漏：NewApiClient logout/安全投影、服务端持久释放及失败候选补偿、真实测试finally清理。不能只新增catch吞掉失败。
2. 上游新增容量挑战、原子并发准入、幂等交付、清理凭据与版本化闲置政策；基于固定版本提交可复核补丁和镜像，不直接改运行中的二进制或热写数据库定时脚本。
3. contracts→API→api-client/主进程→共享features接管理与满额登录；UI只按已声明能力开放，Windows共享边界不破坏、原生验收仍延期。
4. 再做PC Web/Mobile Web/macOS Electron实际认证、主动释放、断线/新PID/重放，以及原真实同步/收费方案验收。正式发布单独记录部署结果；本次应急SQL不等同新版本上线。

验收必须包含：

- 普通登录→退出后上游活跃数回基线，错误密码不列设备；2FA未完成不能进入容量挑战。
- 49/50边界及两进程抢最后名额，容量不会越界；100次签发限制保留，不以撤销/清理绕过。
- 7天闲置/30天绝对期限的前一刻、临界点、后一刻；旧会话时间未知、存活后台轮询和前台交互分别覆盖。
- 跨owner/SID/issuer/过期/改密码/重放/伪造设备标识拒绝，挑选依据变化时不擅自换目标。
- 挑战仅可列会话和完成该登录，额度、生成、MCP等所有普通能力不可用。
- 列表不含凭据；前端、日志、报告、数据库明文和导出扫描；错误请求不能引入任意upstream地址。
- 离线退出、刷新中退出、DB回滚、Redis丢写/延迟fill、上游成功后断线、API/worker/Desktop崩溃恢复，补偿不丢失、不误撤新账号。
- 选择/确认/取消/错误/重试/过期/换号与键盘焦点、窄屏44px触区、长列表可达；完整check/E2E及新包测试，不能沿用旧源码结果。

设计采用UI/UX技能的显式破坏性确认与成功反馈建议，实施沿仓库既有Dialog/Sheet、AlertDialog及语义token，没有新增视觉体系。
