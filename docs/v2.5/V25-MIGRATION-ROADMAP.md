## 3. 开发前必须固定的范围

### 3.1 费用审批和云端 Agent 的边界

[Cloud MCP manifest](../../apps/api/src/modules/mcp/manifest.ts)与[交付计划](./V25-DELIVERY-PLAN.md)明确：云端 MCP 的生图/审批/花费预留流程在 v2.5 休眠。普通 Web 生图当前以 `approvalStatus=not_required` 入队；本地 Automation 有预算及用户确认。

默认沿用当前规范：补现有入口的费用/预算/确认/审计；Cloud MCP 保持只读。只有用户在后续任务中明确要求恢复休眠功能，才增加独立契约、API、状态机和用户审批流程。管理员不能替用户授权花费。

### 3.2 “市场”与管理员后台

当前市场合同是 GitHub 仓库候选搜索（仓库/许可/ref/commit/stars/风险摘要）。G-CLOUD-04 负责把这种发现能力迁到云端，不隐含交易、用户投稿、分成或审核平台。

管理员后台在 2026-09-07 初始讨论时为建议增量；随后已启动的 goal 明确要求“如果全部完成，则开始开发管理员端”。因此 G-OPS-01..03 已获后续开发授权，依赖剩余 v2.5 迁移全部闭合后启动，不倒置为迁移前置，也不提前计入当前已交付功能。建议增加一个规模受控的运维后台：运行、费用回执、身份恢复与GC已经跨多个服务，后台能减少依赖人工查库的排障成本。先提供运行观察、任务排障、用户/授权诊断；账号、额度、兑换码与模型渠道继续委托 New API。需要服务端角色授权和审计，不能只隐藏导航。

## 4. 剩余任务为什么要这样拆

1. **云端方案是首要功能缺口。** 资产、异步会话、权威运行和包后端已存在，重点是接完共享产品、原请求恢复及真实生命周期。复用现有服务，按消费者逐个替换旧501接缝，并保留兼容性负例。
2. **Worker 和 GC 是可靠性缺口。** 现有 lease/epoch/cleanup 代码应保留并补竞争与重启测试，不能以管理页按钮替代恢复语义。
3. **迁移和同步是数据安全缺口。** synthetic 回放已存在，后续重点是真实脱敏语料、完整升级/恢复和真 API 两设备验证。
4. **发布是独立交付缺口。** 本地成功不能证明各平台安装包成功；现有 `deploy:prod`/`deploy:rollback` 仍包含 v1.1 路径和服务名，必须在 G-RELEASE-04 改造验证后才能按新链执行。
