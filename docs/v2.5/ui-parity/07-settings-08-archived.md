# 07-08 设置 · 已归档聊天 — 旧版 vs v2.5 对照

> **旧版源码**:`ArchivedChatsSection`(253 行)。
> **新版**:**无对位实现**。V25-UI-SPEC §0.2 登记「归档会话浏览:暂缓;会话『归档』动作保留,归档列表入口在设置(§6)占位」——当前连占位入口也还没有。

---

## 1. 结论与迁移状态

这是一个**单向阀风险**分区:v2.5 侧栏会话行的「归档」动作已实现(02 §3),用户每天都可以把会话归档——但**没有任何界面能看到、恢复或删除已归档的会话**。归档目前是只进不出的黑洞,数据无损(软归档,`archivedAt` 字段)但用户会感知为「对话丢了」。因此虽然旧版把它排在设置末位,**v2.5 里它的优先级应显著提前(P1)**:凡是暴露了入口的操作,其逆操作必须可达(I2 精神)。

## 2. 旧版结构存档(恢复基准)

- **分区壳**:标题「已归档聊天」+ 刷新钮(`settings-archived-refresh`)。
- **归档记录卡**:「恢复暂时收起的聊天,或删除不再需要的记录」。
- **列表行**:会话标题 + 归档时间(**含年份**——设置评审 P2-7:归档项常跨年,MM/dd 分不清)+ 行动作「恢复 / 删除」。
- **状态矩阵**:loading(`settings-archived-loading`「正在读取归档聊天…」)/ 错误(`settings-archived-error` 就地 alert + 重试)/ 空态(「没有已归档的聊天」)/ ready。
- **交互细节**(评审修过的坑,恢复时直接继承):
  1. 恢复成功 toast「聊天已恢复 · {title}」;失败**就地 toast 不吞错**(评审 A-1:早期版本失败静默);
  2. 删除是永久删除,走确认对话框,成功 toast「聊天已删除」;
  3. 列表读取错误时**仍显示错误而非抢占为空态**(评审注释:错误分支优先于空态分支);
  4. 恢复后的会话回到侧栏列表(按 `updatedAt` 落位)。

## 3. v2.5 迁入设计

| 决策点 | 建议 |
|---|---|
| 入口位置 | 设置「数据」卡内加第三行「已归档对话」(与两个回收站入口并列,复用 screen-intent 模式)或独立卡;**分组导航恢复后升为独立分区**(承旧) |
| 承载形态 | 迁移期:设置内卡 + 列表(行数通常少);会话数大时再分页 |
| 契约 | `workbench.listSessions({ archived: true })`——契约 `archivedAt` 字段已在,api/桥的 list 查询加 archived 过滤参数即可 |
| 恢复动作 | `updateSession({ archived: false })`(桥/服务已有 archived 语义);恢复后 invalidate 会话列表 |
| 删除动作 | 与 02 §3 删除对话同 mutation(AlertDialog 文案:「已生成的图片仍保留在生成历史中」口径一致) |
| 未读/置顶 | 归档时已清(02 已实现离场清理);恢复时不还原置顶(符合旧行为) |

## 4. 交互与文案口径(恢复时不可降级)

1. 时间**必须含年份**(yyyy/MM/dd HH:mm)。
2. 错误分支优先于空态分支;失败操作就地 toast 带原因。
3. 删除永久且有确认;恢复即时无确认(可逆动作,I3)。
4. 空态文案给去处:「没有已归档的聊天。在侧栏对话上选择『归档』可以把暂时不用的对话收到这里。」(承旧意图,新写)。
5. 刷新钮保留(归档可能由其他设备/automation 产生,桌面本地场景弱但云端场景真实)。

## 5. 动效与 UIUX 细节

- 行动作 hover 渐显(与 02/04/05 行动作组同口径);触屏常显。
- 恢复成功后该行离场:旧版直接消失;可选 150ms fade-out(过 reduce 闸门),不做也合格。
- 列表行结构复用 `SessionRow` 的骨架(状态点/标题/动作),但无状态点、无行内重命名——**不要**共享组件,避免为归档场景给 SessionRow 加分支(各自 ~40 行更干净)。
- a11y:恢复/删除钮 `aria-label` 带会话标题(旧版口径「归档聊天:{title}」同法)。

| 状态 | 旧版表现(含评审修复口径) | 恢复要求 |

## 5.2 与会话生命周期的完整闭环(设计校验)

归档会话在 v2.5 数据模型中的完整旅程,恢复本分区后逐段核对:侧栏「归档」(02,已有)→ `archivedAt` 置值 + 离开侧栏列表 + 清置顶/清活动态(已有)→ **设置归档列表可见(本篇 P1)** → 「恢复」→ `archivedAt` 置空 → 回侧栏(按 updatedAt 落位,不还原置顶)→ 或「删除」→ 软删(`deletedAt`)→ 该会话的生成记录仍在历史屏(删除对话确认文案的承诺)。边界:归档会话若仍有 running 任务——旧版允许归档不打断任务,任务完成后未读点规则不触发(归档不在侧栏)——新版桥/api 行为待核,验收时加一条「归档进行中会话:任务照常完成,恢复后可见结果」。

云端多设备:A 设备归档、B 设备侧栏应在下次 refetch 消失(现有 invalidation 已覆盖);B 设备恢复、A 设备下次 refetch 回列表。无实时推送需求(轮询/切屏 refetch 足够),不为此加通道。

## 5.3 为什么不复用回收站 UI

归档与回收站语义不同且不可混淆:归档=整理(可逆、无倒计时、正常数据),回收站=删除缓冲(指向清除)。旧版把归档放设置而非会话列表内 tab,是刻意降低它的日常存在感(归档应该「收起来」)。恢复时维持这个信息架构决策——不在侧栏加「已归档」分组,不与回收站共用视图组件;入口深度(设置 → 数据/独立分区)就是产品设计的一部分。
