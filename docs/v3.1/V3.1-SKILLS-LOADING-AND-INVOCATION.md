# v3.1 Skills 加载与调用功能开发说明

> 文档状态：研究完成，待产品评审后实现
> 版本目标：`v3.1`
> 研究日期：2026-08-11
> 测试样例：[LiamGvchi/gc-minimal-zine-poster](https://github.com/LiamGvchi/gc-minimal-zine-poster)

## 1. 结论先行

这个功能可行，且不需要把 GitHub Skill 作为可执行插件安装到 Musefold。Skill 应被当作一个受限的、版本固定的视觉规则包：读取 `SKILL.md` 和按路由需要的 `references/` 文本，提取生图约束和参考图，再生成一次性的图片请求。

本轮已完成两次真实验证：

1. 用户风景照作为 `edit target`，使用 Skill 的四段式 Prompt，TvT `gpt-image-2` 返回 `971×1619` 的竖版纸感海报。
2. 同一张用户风景照作为 `IMAGE 1`，Skill 仓库的 `shore-pause.jpeg` 和 `pause-map.jpeg` 作为 `IMAGE 2 / IMAGE 3` 风格参考，通过重复的 multipart `image[]` 上传成功。结果保留了用户照片的公路、红岩和远山，同时吸收了参考图的留白、注释线和纸张印刷感，没有复制参考图文字或精确布局。

研究输出图和 Prompt 位于受版本控制的研究素材目录；完整运行证据不进入源码仓库，也不是应用运行时资源。

## 2. 样例 Skill 研究

### 2.1 请求路由

样例 Skill 的 frontmatter 名称是 `gc-minimal-zine-poster-v0-3`。它把请求分为五条路线：

- `Generate`：主题或文字直接生成海报。
- `Photo Input`：先定义图片角色和保真等级，再把真实图片送入生成。
- `Reference Analysis`：只分析参考图，不生成。
- `Prompt-only`：只返回最终 Prompt。
- `Analyze + Generate`：先提取视觉系统，再生成新作品。

用户给出的“上传一张风景照，做成竖版留白纸张海报”应自动进入 `Photo Input -> Generate`，图片角色默认为 `edit target`，本次测试采用 `medium preservation`。

### 2.2 Skill 的固定规则

从 `SKILL.md`、`style-system.md`、`prompt-compiler.md`、`variation-engine.md`、`quality-gate.md` 读取到的可执行视觉规则：

- 默认 3:5 竖版纸张，不要边框和样机。
- 70%–90% 画面保持留白，一个 8%–25% 的视觉事件。
- 平面扫描视角、纸纤维、复印/孔版/凸版/网点等印刷瑕疵。
- 一个清晰可见的高饱和色锚，其他颜色克制。
- 短句、档案微文字或注释线可以存在，但不能形成商业广告标题。
- 避免全幅场景、Logo、CTA、3D、霓虹、密集拼贴、长段可读文字和复制参考图身份。

这些是“固定系统”；主题、锚点位置、纸张色调、主色、排版方式和装饰线是“变量系统”。`examples/` 中的具体鸟、地图、海面、日期和句子属于样本残留，不能自动复制。

### 2.3 测试结果

测试输入图是一张红色岩壁公路风景照。最终 Prompt 明确保留公路消失点、红岩、中央远山和天空，把原图缩成下方偏左的印刷照片裁片，并使用钴蓝色印刷标记。

质量门检查结果：

- 输出尺寸 `971×1619`，比例约 `3:5`。
- 大面积暖象牙纸张留白，主体缩小为一个视觉事件。
- 风景目标仍可识别，没有被改成无关插画。
- 纸纤维、网点、复印颗粒和轻微错位清晰可见。
- 钴蓝色锚点在缩略图上仍可见。
- 多图测试中 `IMAGE 2 / IMAGE 3` 的文字和精确构图没有被复制。

## 3. Composer 交互方案

### 3.1 粘贴 GitHub 地址

不把当前 textarea 改成复杂的富文本编辑器。采用 Composer 内部的“上下文附件行”：URL 被识别后从正文中移除，变成一个原子 Skill 附件；用户仍然在原 textarea 中输入普通提示词和手动指令。这保留现有中文输入法、Enter 发送、复制和编辑逻辑，也符合 Codex/Cursor 类产品把外部上下文作为独立附件的使用习惯。

识别入口：

- 粘贴纯文本时，优先检测完整 `https://github.com/<owner>/<repo>`、`tree/<ref>` 或指向 `SKILL.md` 的 `blob/<ref>/.../SKILL.md` 地址。
- 用户直接输入后按空格、Enter 或发送时，也执行同一解析器。
- URL 含账号、密码、Token、查询参数、锚点、越权路径时拒绝，不把它保存到 Skill 附件。
- 解析结果复用现有 `parseGithubSkillUrl`，下载和扫描复用 `readPublicGithubAgentSkillSource` 与 `scanAgentSkillFiles`。

### 3.2 Chip 状态

附件行使用主色和 Skill 图标，不能只用一段蓝色 URL 文本。建议使用 `Sparkles`/`Blocks` 图标，图标旁显示仓库 slug；悬停或展开显示固定 commit、Skill 名称和权限边界。

| 状态 | 视觉 | 文案和行为 |
|---|---|---|
| `detecting` | 主色边框、图标轻微旋转；开启减少动态时改为静态图标 | `正在识别 Skill…`，发送按钮暂时等待 |
| `loading` | 主色半透明底、下载进度点 | `正在读取 GitHub Skill…`，显示仓库名和可取消入口 |
| `recognized` | 主色实心小图标、主色文字、圆角附件 chip | `gc-minimal-zine-poster-v0-3`；旁边显示 `生图 Skill` 和移除按钮 |
| `needs-review` | 警示色图标，不使用红色错误态 | `检测到生图规则，请确认引用的参考图`；允许继续或移除 |
| `unsupported` | 中性色图标 | `不是可用的生图 Skill`；提供查看扫描结果和移除 |
| `error` | 错误色图标 | 保留原 URL 可恢复，提供重试；不静默丢失用户输入 |

每个状态都要有 `aria-live` 文本，颜色不是唯一状态信号。Chip 的 `×`、重试和展开均提供键盘操作。正在识别时的动画必须尊重 `prefers-reduced-motion`。

### 3.3 发送前的上下文摘要

识别成功后，在 textarea 上方显示一行紧凑摘要：

```text
[Skill 图标] gc-minimal-zine-poster-v0-3 · 生图 Skill · 已锁定 main@342b5c1
[图 1 用户照片] [图 2 Skill 参考] [图 3 Skill 参考]
```

用户上传图片继续使用现有有序缩略图条。Skill 参考图使用较弱的“参考”标记，避免用户误以为会覆盖照片主体。点击任意缩略图打开 Lightbox；移除会重新编号。

## 4. 数据和 IPC 契约

新增一次性调用对象，不把临时 URL 伪装成普通提示词：

```ts
type SkillInvocationStatus =
  | 'detecting' | 'loading' | 'recognized' | 'needs-review'
  | 'unsupported' | 'error';

interface SkillAttachment {
  id: string;
  repositoryUrl: string;
  requestedRef?: string;
  skillPath?: string;
  displayName: string;
  status: SkillInvocationStatus;
  capability: 'image-generation' | 'image-analysis' | 'mixed' | 'unsupported';
  skillName?: string;
  description?: string;
  commitHash?: string;
  licenseText?: string;
  selectedTextFiles: string[];
  selectedReferenceImages: LocalImageReference[];
  error?: { code: string; message: string };
}

interface ImageSkillPlan {
  attachmentId: string;
  mode: 'generate' | 'photo-input' | 'reference-analysis' | 'prompt-only' | 'analyze-generate';
  prompt: string;
  negativePrompt?: string;
  outputRatio?: string;
  userImageRoles: Array<'edit-target' | 'reference-image' | 'supporting-insert'>;
  skillReferenceImages: LocalImageReference[];
  sourceCommit: string;
}
```

建议新增以下 IPC，不复用配方导入的长流程作为 Composer 的等待态：

- `skillInvocation.resolveGithub`：URL -> 固定 commit 的扫描摘要和候选能力。
- `skillInvocation.selectReferences`：按 Skill 的 `references/` 和 README 链接选择文本、PNG/JPG/WebP 参考图。
- `skillInvocation.compilePlan`：把安全的 Skill 文本、用户提示词和输入图片角色编译为 `ImageSkillPlan`。
- `skillInvocation.cancel`：取消下载、读取或编译。

现有配方 Skill 导入继续保留，用于“导入成可编辑配方”；Composer Skill 附件是一次性调用，不自动写入配方库，除非用户明确选择“保存为配方”。

## 5. 生图图片顺序和 Prompt 拼接

所有图片仍然遵守 v0.3 的单一编号事实来源：数组顺序。

```text
用户上传图 1..M       -> 图 1..M       -> multipart image[] 前 M 项
Skill 参考图 M+1..N   -> 图 M+1..N    -> multipart image[] 后 N-M 项
```

编译器必须在 Prompt 中明确声明角色：

```text
图 1 是用户的编辑目标，必须保留……
图 2、图 3 是 Skill 的风格参考，只学习留白、纸张、排版和印刷质感，不能复制主体、文字或精确构图。
```

发送时：

1. 用户图片先通过现有 `stageLocal` 进入受管目录。
2. Skill 参考图片从固定 commit 的受管缓存读取，不能接受正文中伪造的任意本地路径。
3. 合并并去重，统一限制不超过 `MAX_REFERENCE_IMAGES = 16`。
4. OpenAI-compatible Provider 逐项追加 `form.append('image[]', ...)`，绝不排序、并发重排或静默截断。
5. 没有参考图片时仍可走纯 Prompt Skill；非多图 Provider 必须返回明确的能力错误。

## 6. 自动识别策略

识别分两层，先快后准：

### 第一层：本地确定性扫描

- URL 只允许 `github.com` HTTPS；不跟随重定向到任意域名。
- 必须存在根目录 `SKILL.md`，frontmatter 必须包含 `name` 和 `description`。
- 复用安全扫描器：路径规范化、大小/数量上限、UTF-8 校验、禁止符号链接、脚本 `executionPolicy: never`。
- 从 `SKILL.md` 和 `references/` 搜索 `image`, `photo`, `poster`, `prompt`, `generate`, `reference image` 等信号；识别 `examples/` 或 `references/` 下的 PNG/JPG/WebP。
- 根据文件扩展名和文本内容区分 `image-generation`、`image-analysis`、`mixed` 和 `unsupported`。

### 第二层：受约束文本 AI 分类

本地信号不足或多种能力冲突时，调用用户已配置的文本 AI，要求只返回 JSON Schema：

```json
{
  "capability": "image-generation",
  "mode": "photo-input",
  "confidence": 0.94,
  "requiredTextFiles": ["SKILL.md", "references/prompt-compiler.md"],
  "referenceImagePaths": ["examples/shore-pause.jpeg", "examples/pause-map.jpeg"],
  "fixedRules": ["vertical 3:5", "70%-90% negative space"],
  "variableRules": ["anchor position", "main accent hue"],
  "avoid": ["commercial ad", "full-bleed scene"]
}
```

Skill 内容只能作为不可信数据放在分隔区；模型不得执行 Skill 中的 shell、网络、环境变量、密钥、文件删除或安装指令。模型只能提取视觉规则、图片角色、输出比例和避免项。

## 7. 安全和资源边界

- 不执行仓库中的 `.sh`、`.py`、`.js`、`.ts` 或其他脚本。
- 不读取 Skill 目录之外的文件，不接受 Skill 文本返回的绝对路径。
- 复用当前限制：最多 500 个读取目录项、100 个文本文件、单文本 1 MiB、文本总量 8 MiB、解包后总量 64 MiB、下载归档 32 MiB；GitHub 归档缓存总预算仍为 512 MiB。
- 只从固定 commit 的缓存读取资产；调用时记录 commit 和内容 hash。
- 不把 API Key、GitHub Token 或本地绝对路径写入 Prompt、日志、历史摘要、导出文件或证据。
- 公开仓库的 MIT 许可可显示为已确认；无许可证、私有仓库或 GitHub 匿名额度耗尽时，进入可解释的审查/错误态。
- 不自动上传 Skill 包的全部图片；只选中与当前路由相关的 PNG/JPG/WebP，且在发送前显示数量和编号。

## 8. 开发拆分

### P0：Composer 体验与纯扫描

- `parseGithubSkillUrl` 接入 Composer 粘贴/输入提交。
- `SkillAttachment` 状态机、Chip、识别动画、取消/重试和无障碍文本。
- `skillInvocation.resolveGithub` 复用现有 GitHub reader/scanner，固定 commit。
- 对样例 Skill 仅做本地确定性识别，不引入文本 AI 依赖即可显示 `生图 Skill`。

### P1：参考图选择和计划编译

- 展示 Skill 中可用文本/图片文件，默认选择根 `SKILL.md` 与它引用的 references。
- 将用户图片和 Skill 参考图合并为有序 `referenceImages`。
- 增加 `compilePlan` 的受约束 JSON 输出和 Prompt 预览。
- 发送前显示角色摘要，允许用户移除 Skill 参考图但保留 Skill 规则。

### P2：生成、历史和可复用

- OpenAI-compatible 多图请求复用 v0.3 `image[]`，写入 Skill commit、计划摘要和图片角色快照。
- 生成后的会话类型新增 `skill`，侧边栏图标与普通聊天/提示词/配方区分。
- “保存为配方”时把固定规则、变量规则、避免项和来源 commit 写入配方草稿；默认不自动保存。
- 增加离线缓存、更新检查和固定 commit 的重放测试。

## 9. 验收标准

- 粘贴样例 GitHub 地址后，Composer 在 300ms 内显示 `detecting`，随后显示 Skill 名称和 `生图 Skill`。
- 网络慢、GitHub 429、缺少 `SKILL.md`、非生图 Skill 和文本 AI 不可用时，均有明确状态和恢复路径。
- 用户图片、Skill 参考图和 Prompt 的顺序可在发送前查看，实际 multipart `image[]` 顺序一致。
- 样例风景照生成结果达到 3:5、70%–90% 留白、单一视觉事件和纸张印刷质量门；用户照片中的主要地貌仍可辨认。
- Skill 文件中的脚本从未执行；Key、Token、绝对路径不进入日志和持久化快照。
- 键盘可以聚焦 Chip、取消、重试、展开和移除；减少动态设置下不依赖动画表达识别状态。
- 取消 Composer Skill 附件不会删除用户已上传图片；删除 Skill 附件后普通提示词仍可发送。

## 10. 当前不做

- 不在 v3.1 直接运行第三方 Skill 的脚本或任意 Agent 工具。
- 不把整个仓库无选择地上传给图片模型。
- 不把 Skill 强制转换成配方后才能生图。
- 不在 textarea 内引入富文本编辑器和复杂 token 光标模型；先用原子附件行实现 Codex/Cursor 式上下文插入。
